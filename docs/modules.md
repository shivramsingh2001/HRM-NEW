# Modules Reference

Functional/business-logic reference for the Laravel HRMS app at `D:\HRMNEW\hrm (3)`. Route line numbers refer to `routes/web.php` (admin panel, Blade) and `routes/api.php` / `routes/api_v1.php` (mobile/external API) as they stood 2026-09-16. Business rules below were read directly from controller/service code — not inferred — but controllers are large (several exceed 1,000 lines) so treat each module section as "verified highlights," not an exhaustive line-by-line spec. Re-grep the cited file before relying on an exact rule for anything payroll- or money-related.

## Cross-cutting concerns (apply across most modules below)

**Multi-tenancy**: every table has `tenant_id`; a `tenant` middleware group wraps all of `web.php`/`api.php`. See `docs/architecture.md` for the resolution mechanism.

**Two permission layers, both in active use, not a clean migration**:
- Coarse: `role:admin`, `role:hr`, `role:manager`, `role:employee` (or comma lists like `role:admin,hr`) — `app/Http/Middleware/RoleMiddleware.php`.
- Fine-grained: `permission:{module},{action}` — `app/Http/Middleware/EnsurePermission.php` → `App\Services\RbacService::can()`. `admin` role always bypasses. Used alongside `role:` in the same route file (e.g. leave, expenses, overtime, meetings, payroll, task approval). Controllers additionally call a `scopeCoversOwner($authUser, $module, $action, $ownerUserId)` helper (seen in `LeaveController`, `ExpenseController`) to check whether the acting manager's scope actually covers the specific employee being approved — this replaced an earlier bug where any manager could approve any employee's request.
- `feature:{key}` — `app/Http/Middleware/EnsureFeatureEnabled.php` → `App\Services\FeatureService::enabledForCurrentTenant()`. Gates whole modules by subscription plan (currently applied to `payroll` and `recruitment` route groups). No tenant context = allow.

**Generic multi-level Approval Workflow Engine** (`App\Services\Approvals\ApprovalService`, Tier 2/T2-A): a tenant can configure a named workflow (`approval_workflows` + `approval_workflow_steps`, managed at Settings → Approvals, `app/Http/Controllers/Settings/ApprovalWorkflowController.php`) for a request type. `ApprovalService::decide($type, $subject, $actor, $action, $remarks)` is called from the *old* single-approver controller code; it returns `null` if no workflow is configured for the tenant (falls through to legacy direct-approve code unchanged), or drives the subject through the configured levels (role / user / reporting_head / department_head approvers, quorum `all` or first-wins, per-level SLA with `auto_approve` / `escalate` / `notify` breach action via a scheduled `tick()`). Registered handlers (`request_type => handler class`) in `ApprovalService::HANDLERS`:
  - `regularization` → `RegularizationApprovalHandler`
  - `overtime` → `OvertimeApprovalHandler`
  - `leave` → `LeaveApprovalHandler`
  - `payroll_revision` → `PayrollRevisionApprovalHandler`
  - `payroll_bonus` → `PayrollBonusApprovalHandler`
  - `payroll_run` → `PayrollRunApprovalHandler`
  Approval delegation (`approval_delegations`, date-scoped) is honored in `currentApprovers()`. Also supports delegate-aware notifications via `App\Notifications\CustomNotification`.

**Notifications**: most write-actions fire an in-app `Notification` (Laravel notifications table) plus FCM push (`App\Services\FirebaseService`) via per-module `*NotificationService` classes (`LeaveNotificationService`, `ExpenseNotificationService`, `OvertimeNotificationService`, `AttendanceNotificationService`, `AttendanceRegularizationNotificationService`, `TaskNotificationService`, `RequestNotificationService`, `MeetingNotificationService`, `AnnouncementNotificationService`, `ExpensePaymentNotificationService`). These are consistently wrapped in `try/catch` so a notification failure never blocks the underlying transaction.

## Auth

- **Web**: `App\Http\Controllers\Auth\AuthController` — session login (`/login`), forgot-password. `role:` middleware then routes to one dashboard per role.
- **Mobile/API**: `App\Http\Controllers\Api\Auth\AuthController` — `POST /api/login` (JWT via `auth:api` guard, see `docs/architecture.md`), `POST /api/send-otp` + `POST /api/login-otp` (OTP login, throttled `otp-request`/`otp-verify`), forgot/reset password, change password, face registration flag (`GET /api/user/face-registration`), device logout, account delete (`GET /api/delete`).
- `singleLogin` middleware (`CheckSingleDeviceLogin`) enforces one active session per user on the API guard — routes/api.php:48.
- Super Admin Panel impersonation handoff: `GET /impersonate/consume` (no auth guard — issues a login) and `POST /impersonate/end`, `App\Http\Controllers\Impersonation\ImpersonationController`. `EnforceImpersonationExpiry` middleware presumably time-boxes the session (see `docs/architecture.md` for the full middleware list).
- Login attempts are throttled (`throttle:login`) and logged via `App\Services\LoginAttemptService` / `AuthAuditService`.

## Users / Employee Profiles

- **Multi reporting-head support (2026-09-19)**: an employee can have more than one reporting head, selected via a `select2` multiselect (`reporting_head[]`) on the wizard's Job Details step (`UserController::saveStep3`/`updateStep3`). The full set is stored in the `user_reporting_heads` pivot (`App\Models\UserReportingHead`); the first selected id is written as the "primary" to `user_job_details.reporting_head` (kept in sync on every save) so older single-head read call sites keep working. Canonical helpers: `User::reportingHeads()` / `User::directReports()`, and `User::scopeManagedBy($headId)` (`User::managedBy($id)`) for "my team" queries — this replaced the previous per-controller `UserJobDetail::where('reporting_head', $id)` pattern in `AuthorizesByScope` (all 17+ controllers using that trait) plus ~30 other controllers across Leave/Expense/Overtime/AttendanceRegularization/Task/Loan/Team/Dashboard/Performance/Offboarding (web, `Api/*`, and `AI/*` variants). Decision: when an employee has multiple reporting heads, **any one of them may approve/act** — `ApprovalService::reportingHead()` now returns the full set as a `Collection` (the engine already supported multi-approver "first-wins"/"all" quorum per step); the 7+1 `*NotificationService::getReportingHead()` resolvers were similarly changed to `getReportingHeads()` returning a `Collection`, merged into each module's recipient list. A handful of pure-display spots (report table columns, a couple of team-profile pages) still show only the primary head's name — not yet migrated to the full list, since they're cosmetic.
- **Dynamic employee documents (2026-09-19)**: `App\Models\EmployeeDocument` (table `employee_documents`) replaced the old fixed 4-column approach (`experience_letter`/`tenth_marksheet`/`twelfth_marksheet`/`highest_qualification_certificate` on `user_basic_details`, now deprecated but still read for backward compatibility). The wizard's Documents step posts a dynamic `documents[]` array (type from `EmployeeDocument::$documentTypes` + `other` with free-text `document_type_other`, optional `document_name`, file) with add/remove rows in the UI; `UserController::saveEmployeeDocuments()` is the shared save path (wizard step 7 and the standalone `update()` action both call it) — full-replace semantics per submission (a previously-uploaded document not present in the posted set is removed), validated via `UserController::documentRows()` (file `mimes:pdf,jpg,jpeg,png,doc,docx`, `max:5120`). `UserController::show()` and the mobile `Api\User\UserController` (`documents_list` key, additive alongside the legacy `documents` object) both read from the new table.
- **Known duplication**: the Add/Edit employee UI exists in **three** places — `resources/views/client/user/partials/employee-wizard-form.blade.php` (the active drawer on the employee list page, embedded via `view-user.blade.php`) and two older standalone pages, `add-user.blade.php`/`update-user.blade.php`, still routed from `employee.create`/`employee.edit`. All three were updated for the multiselect; only the drawer got the full dynamic-documents UI — the two standalone pages still show the old 4 fixed file inputs (harmless no-op server-side, but not fixed). Consider retiring the standalone pages.
- Toggle endpoints: `toggle-status` (activate/deactivate), `toggle-face-register`, `update-attendance-type`, `toggle-location-tracking` (field-tracking seat, single user), `bulk-location-tracking` (bulk).
- Export: `export/excel`, `export/pdf` (employee list).
- **Employee ID Prefix (2026-09-30)**: tenant-configurable 2-letter prefix for auto-generated employee IDs (`SH000123` by default), settable at Basic Setup > Employee ID Format (`App\Http\Controllers\Settings\EmployeeIdSettingsController`, `tenants.employee_id_prefix`). Generation is centralized in `App\Services\User\EmployeeIdService::generate()` — both creation paths (`UserController` web wizard and `EmployeeProvisioningService` recruitment onboarding) call it instead of hardcoding `'SH'` as they previously did. Falls back to `config('employee_id.default_prefix')` ('SH') when a tenant hasn't set one. Changing the prefix only affects employees created after the change — existing `employee_id` values are never rewritten.

## Org Structure: Branches, Departments, Designations, Employment Types

- **Attendance Location vs. Branch (2026-09-20 split)**: what used to be a single `branches`/`Branch` concept has been split into two genuinely separate modules, since it always conflated "where can this employee check in from" with "which organizational branch does this employee belong to":
  - `App\Http\Controllers\AttendanceLocation\AttendanceLocationController` (`App\Models\AttendanceLocation`, table `attendance_locations`, routes `attendance-location.*`) — purely the attendance-geofencing entity (name + lat/long + `radius` + `geofence_enabled`). Read by `Api\Attendance\AttendanceController`'s clock-in/out geofence check via `user_job_details.office_branch` (unchanged column name; `0` = "any active, geofence-enabled location"). UI at `client/attendance-location/attendance-location.blade.php` — the all-blue card grid + Leaflet map picker (kept from the original page) + a real delete-confirmation modal (the old page's delete button was dead — JS referenced a modal that didn't exist anywhere in the file).
  - **Attendance Location and Work Type are optional on every employee form (2026-10-01)** — add/edit/wizard (`UserController::normalizeJobLocationInput()` + `jobLocationRules()`: `type` nullable → saved as `office`; `branch` nullable + must be an `attendance_locations` row of the same tenant) and recruitment hire (`OnboardingController::hire`, `EmployeeProvisioningService`). "All Locations"/empty is stored as `office_branch = NULL` (the old `0` violates the `user_job_details_ibfk_1` FK). The empty option is labelled "All Locations" only when the tenant has more than one active location, otherwise "-- None --". Clock-in/out: NULL = nearest geofenced location; if the tenant has **no** active geofenced location the check is skipped (previously "No branches configured" error).
  - `App\Http\Controllers\Branch\BranchController` (`App\Models\CompanyBranch`, table `company_branches`, routes `branch.*`) — the actual organizational Branch: name/address/contact/`branch_head` (FK → users), **no** lat/long/radius/geofence fields at all. Optional — `user_job_details.branch_id` (nullable, new) is only populated by companies with multiple physical branches; a single-location company never touches it. `detail()` shows a read-only profile + "Branch Members" table (mirrors Department's members table) with an **Assign Employees** bulk action (`assignEmployees()`, `assign_type` of user/department/all, adapted from `ShiftController::getUserIdsForAssignment()`) that writes `branch_id` for many employees at once. Gated `role:admin,hr` for mutations, `permission:branches,view` (company-wide, all roles) for reads — the first of the org-structure modules to get real RBAC registration (`config/rbac.php`'s `branches` module); Department/Designation still rely on Blade-level role checks only, unchanged.
  - `ApprovalWorkflow::matchesUser()`'s `applies_to` scoping (`app/Models/ApprovalWorkflow.php`) was split the same way: the pre-existing `branches` key (which actually checked `office_branch`) is now `attendance_locations`; a new `branches` key checks the new organizational `branch_id`. No live data existed for either key at the time of the split (verified before renaming), so no data migration was needed.
  - Both `AttendanceReportController`'s branch-wise attendance report (`DB::table('branches')` → `attendance_locations`) and its two views were updated to match; labels relabeled "Attendance Location Wise" for clarity. A near-identical, unrouted dead-code duplicate of that report (plus an unused `updateEmployeeBranch()`) still sits in `TeamController.php:1810-2510` — left untouched, pre-existing and out of scope.
- `App\Http\Controllers\Department\DepartmentController`, `App\Http\Controllers\Designation\DesignationController` — simple CRUD, index/create/update/detail pattern, no delete route exposed for either. Both list pages (`client/department/department.blade.php`, `client/designation/designation.blade.php`) use the same all-blue card theme from `client/announcement/all.blade.php` (view + edit icons on each card, edit opens a shared modal populated via JS `data-*` attributes); their detail pages (`department-detail.blade.php`/`designation-detail.blade.php`) are read-only — editing was moved off of them onto the list-page card. **Note**: view/edit icon visibility differs pre-existingly between the two modules — Department gates both view and edit to `admin`/`hr`; Designation gates view to `admin`/`hr` but edit to `admin`/`manager` (carried over unchanged from the original detail-page edit button's guard) — not unified during this pass since it wasn't asked for.
- Employment types: model `EmployementType` exists (note the typo is baked into the class/table name); no dedicated controller found in `routes/web.php` — likely managed as a lookup elsewhere (check Settings or seeders if this needs UI).
- Roles/permissions: `roles`, `role_permissions` tables (per `docs/database.md`); runtime checks go through `RbacService`, not a dedicated CRUD controller found in this pass.
- **Mobile app plan access (2026-09-29)**: `GET /api/user/features` (`Api\User\UserController::features`) and a new `data.access` block in both login responses (`AuthService::login()` and `AuthController::login_otp()`) return `App\Services\AppAccessService::forUser()`: `role`, `plan` (active/trial `tenant_subscriptions` joined to `subscription_plans`: name, slug, status, start/end, trial end), `features` (every `config/features.php` key → bool via `FeatureService::allForTenant()` — same resolution as the web: override → subscription snapshot → default, 5-min cache busted by the Super Admin Panel), `enabled_features` (just the true keys), `location_tracking` (`company_enabled` = plan has `geo_tracking` AND `tenants.field_tracking_enabled`; `employee_enabled` = that AND this user holds a seat, `user_job_details.location_tracking_enabled` — the same rule `/user/attendance/track` applies via `FieldTrackingService::resolveForUser()`; plus `ping_seconds`, `mode`, `batch_max` for the app's sender) and `permissions` (`RbacService::effectiveMatrix()`: every `config/rbac.php` module × action → `own`/`team`/`company`/null; admin = company everywhere; `manage` implies view/create/edit/delete). Test: `tests/Feature/MobileFeatureAccessTest.php`.
- **Subscription feature gating enforced (added 2026-09-22)**: `feature:branches` (default OFF) now wraps `branch.*` routes and the Company-settings sidebar entry — previously defined in config but never enforced anywhere (unlike Expense/Project/Loan, no tenant had any `company_branches` rows yet, so no backfill was needed before enabling). `attendance_locations.*` (the geofencing module, distinct from organizational Branches per the split above) is **not** gated by any feature key — out of scope, not raised as a gap.

## Attendance

- Web: `App\Http\Controllers\Attendance\AttendanceContoller` (sic — typo preserved from codebase) — calendar view, sessions.
- Mobile: `App\Http\Controllers\Api\Attendance\AttendanceController` (huge, ~1600+ lines) — `clockIn`, `clockOut`, `history`, `trackLocation`/`trackBatch` (GPS breadcrumbs, throttled `location-ingest`), `today`, `todayLocations`, `regularizationStore` + regularization view/approval endpoints.
- **Clock-in rules** (`AttendanceController::clockIn`, `app/Http/Controllers/Api/Attendance/AttendanceController.php`): requires `lat`, `long`, `address` (min 5 chars); resolves the user's shift for the day; **night-shift date rollback** (now `AttendanceCalculator::resolveAttendanceDate()`, lifted out of this controller so every punch source agrees) — if the shift end time is before its start time (or ends ≤04:00 and starts ≥20:00) and the clock-in happens between 00:00–05:59 before the shift's start hour, the attendance row is dated to the *previous* calendar day; checks for an approved WFH/Travel `Request` covering the date. Geofence/branch resolution is unchanged. The actual write (and the open/closed-session check) is delegated to `AttendancePunchService::capture()` — see "Attendance — multiple punches per day" below. Failed attempts are logged via `createFailureLog()`.
- **Attendance — multiple punches per day (added 2026-09-23)**: `tenants.allow_multiple_punches` (default `false`, toggled on the Attendance Policy settings page alongside `late_halfday_enabled`) controls whether an employee can clock in again after clocking out. `attendances` is no longer written directly by any punch source — it is a **materialized rollup** of the new `attendance_punches` table (one row per raw Clock In/Out event, from mobile GPS, web, manual/admin, biometric, or a future kiosk source), computed the same way for both flag values so there is one derivation path, not two parallel worlds:
  - `App\Services\Attendance\AttendancePunchService::capture(PunchInput $input)` is the single funnel every source calls. Enforces: an `in` while a session is already open is always rejected (both flag values); when `allow_multiple_punches=0`, an `in` is *also* rejected once any session has already completed that day (byte-identical to the pre-2026-09-23 "one clock-in/out pair per day" behaviour); an `out` with no open session is rejected. Also handles period-lock checks, a debounce window (`config('biometric.dedupe_window_seconds')`, shared with the biometric pipeline), and `client_ref`-based idempotency for mobile offline-sync retries. The "is there an open session" lookup is bounded to a few days either side of the incoming punch's own timestamp (not the server's wall clock) so a punch from an unrelated period can never be mistaken for a currently-open session.
  - `App\Services\Attendance\PunchSessionCalculator` is the pure (no-DB) pairing/aggregation algorithm: sorts a day's punches by `punched_at` (so out-of-order/delayed-sync arrivals self-correct), pairs `in`→`out` into sessions, sums worked seconds across sessions, and derives `clock_in` (first session's in), `clock_out` (**null while any session is open, even if an earlier session already closed today** — this preserves `clock_out IS NULL` as "still clocked in" everywhere that invariant is relied on), `late_minutes` (from the first in), and `early_departure_minutes`/`overtime_minutes`/`attendance_status` (from the last out, once the day is closed). An `out` with no preceding `in` (biometric replay/clock skew) is excluded from the math and flagged via `attendances.metadata.needs_review`, never silently dropped.
  - `App\Services\Attendance\AttendanceRollupService::recompute()` is the bridge back to the existing world: it calls the calculator above, then writes the result through the **unmodified** `AttendanceEntryService::record()` funnel — so period-lock enforcement, the `attendance_logs` audit trail, `LatePolicyService`/`AttendanceSummaryService` recompute, and `AttendanceDomainEvent` emission all keep working exactly as they do for every other write path.
  - The mobile `clockIn()`/`clockOut()` controller methods keep all of their existing geofence/WFH/night-shift-rollback logic verbatim; only the final "write the row" step was swapped for a call into `AttendancePunchService::capture()` — this also closes a pre-existing gap where the mobile path bypassed period-lock checks and never emitted `AttendanceDomainEvent`. `BiometricAttendanceService::apply()` (see Biometric section below) branches on the tenant flag: `=0` tenants keep their original single-pair-fold behaviour completely unchanged; `=1` tenants route through the same `AttendancePunchService` funnel so a 3rd+ punch opens a new session instead of being discarded.
  - New read-only mobile endpoints, additive: `GET /api/user/attendance/punches?date=` (raw punches + paired sessions for one day) and `GET /api/user/attendance/current-session` (cheap open/closed status for the clock-in/out button state).
  - Historical `attendances` rows were backfilled into `attendance_punches` on migration (`source='backfill'`, one synthetic `in`/`out` pair per existing `clock_in`/`clock_out`); `attendances.session_count` is `1` for every pre-2026-09-23 row and every `allow_multiple_punches=0` day going forward.
  - Biometric days written while `allow_multiple_punches=0` (`BiometricAttendanceService` single-punch path) have no `attendance_punches`. If the flag is switched on mid-day, the next device punch first adopts that row (`adoptSinglePunchDay`: synthetic `in`/`out` pair, `metadata.adopted_from_attendance`), so it opens session 2 instead of being rejected as "set manually". Only rows with `attendances.metadata.source='biometric'` and a non-`manual` `attendance_type` are adopted. To recover punches already skipped: `php artisan biometric:reprocess --remap --since=<date>`.
  - Reports/analytics/payroll/the AI export API/the B2B `AttendanceV1Controller` were **not changed** — they all read `attendances`/`attendance_summaries`, whose values are unaffected for `allow_multiple_punches=0` tenants by construction (same funnel, same numbers).
- **Late Arrival / Early Leaving policy** (`App\Services\Attendance\LatePolicyService::recalculateMonth`) — Feature B, generalized 2026-09-22 from late-only/half-day-only into two fully independent rule sets, still the *sole writer* of `attendances.effective_status`/`day_fraction`/`policy_note`, deterministic/idempotent, re-runnable any time:
  - Manual rows (`attendance_type = manual` or has `marked_by`) are authoritative and never reclassified from worked hours.
  - `on_leave`/`absent`/`holiday`/`weekoff` → 0.0 day fraction; `half_day`/`first_half_leave`/`second_half_leave` → 0.5.
  - Otherwise worked seconds are computed (`AttendanceCalculator::workedSeconds`, capped at 24h) and classified by `AttendancePolicySnapshot::classify()` against the tenant's policy in force **on the 1st of that month** (a later policy change never retroactively re-grades a closed month).
  - **Grace period source** (`attendance_policies.grace_mode`, `'fixed'`|`'shift'`, default `'fixed'`): `'fixed'` uses one flat tenant-wide `fixed_grace_minutes` value regardless of shift (this is what every tenant effectively already had, so it's the migration default, backfilled from the old `grace_minutes` — zero drift); `'shift'` uses each day's own `shifts.grace_minutes` instead. Shared by both late and early — edited from the Late Arrival card only (`AttendancePolicySnapshot::graceMinutesFor()`).
  - Each `late`/early-leaving day re-checks the existing `attendances.late_minutes`/`early_departure_minutes` columns (already computed once, correctly, against the shift's own grace at punch time) against the resolved grace value above, incrementing independent per-user monthly counters (`monthlyLateAllowance` / `monthlyEarlyAllowance`). Once either counter exceeds its allowance, that rule's **attendance action** (`late_attendance_action`/`early_attendance_action`, one of `none`/`half_day`/`absent`, default `none`, labeled "Keep Original Attendance" for `none` in the UI) fires — `none` leaves `effective_status` completely untouched; the raw `late_minutes`/`early_departure_minutes`/`policy_note` audit trail is preserved either way. A day in excess on both rules converges to the more severe outcome (downgrade only ever moves present→half_day→absent, never back). A regularized row is never counted toward either allowance and never downgraded.
  - **Payroll deduction is a fully independent second toggle**, not tied to the attendance action at all: `late_deduction_enabled`/`early_deduction_enabled` gate it; when on, `late_deduction_mode`/`early_deduction_mode` (added 2026-09-30, enum `fixed_amount`/`half_day`/`full_day`/`custom_multiplier`, default `custom_multiplier` for zero-drift on pre-existing rows) selects how the per-excess-day amount is computed: `fixed_amount` uses `late_deduction_amount`/`early_deduction_amount` (a flat rupee amount) verbatim per excess day; `half_day`/`full_day` hardcode 0.5x/1.0x of the daily rate; `custom_multiplier` uses `late_deduction_multiplier`/`early_deduction_multiplier` (e.g. 0.3x = 30% of a day's salary, 1.5x = 150%). `App\Services\Payroll\LateEarlyDeductionCalculator::calculate()` → `amountForExcess()` computes `excess_days * (mode-specific rate)` (daily rate = `basic_salary / payroll_masters.ot_rate_divisor_mode` divisor, the same one overtime pricing already uses) and is injected as a `late_deduction`/`early_deduction` line item by **both** payroll engines (`PayrollCalculationEngine` and `MonthlyPayrollController`), persisted on `monthly_payrolls.late_deduction`/`early_deduction` columns. `LatePolicyService::excessCounts()` is a pure, zero-write read the calculator uses — this is what guarantees the deduction can never accidentally touch attendance status, and vice versa.
  - Settings: Company Policies page (`workforce.blade.php`, `role:admin,hr`), two `col-md-4` cards after Day Classification — Late Arrival (`late-policy-settings.update`) and Early Leaving (`early-leaving-policy-settings.update`) — each a standalone form following the same read-current-policy-then-merge-on-top pattern as Day Classification (`AttendancePolicySnapshot::toPersistableArray()`), so saving one card never resets fields owned by another. The older big Attendance Policy form (`attendance-policy.update`) also carries these fields forward unchanged, with one exception: its own `late_halfday_enabled` checkbox, when explicitly checked, still sets `late_attendance_action='half_day'` (but unchecking it never silently downgrades an `'absent'` choice made via the new card). ## Shift Management

- **Company-wide vs. employee-wise mode**: `tenants.custom_shifts_enabled` (toggle at `Settings\ShiftSettingsController`, `shift-settings.*`, `role:admin,hr`, **not** gated by the `shifts.custom` middleware below so the toggle screen is always reachable). OFF = the whole company runs on one fixed shift (`tenants.default_shift_id` + `default_weekoff_days`, applied company-wide by `regenerateWeeklyOffs()`); every other `shift.*` route is unreachable while OFF. ON = per-employee assignment via `shift_assignments`/`user_shifts` below. `App\Services\Attendance\TenantShiftResolver::forUserDate($userId,$tenantId,$date)` is the single resolver for "what shift applies to this user on this date" — OFF path unconditionally returns the tenant default (status not checked, so an admin can still edit a disabled default); ON path is an exact-date lookup on `user_shifts` (`Shift.status=1` required, else `null`). **This resolver's code has not changed** since the Permanent/Flexible feature below shipped — see the write-time note.
- Definitions CRUD: `App\Http\Controllers\Shift\ShiftController` (`index/store/update/change-status/destroy`, `shift.*` routes, `role:admin,hr`) manages `shifts` rows (name/times/grace/break/color; `total_hours` computed server-side via `computeTotalHours()`, handles midnight-crossing when `end_time <= start_time`).
- Roster/assign UI: `shift.roster` (`role:admin,hr,manager`, manager sees only their reportees) — two tabs: **Roster** (day/week/month grid) and **Existing Assignments** (admin/hr, filterable list + bulk edit/delete/export, `getUserShiftsData`). "Assign Shift" is a modal on this page (`POST shift.assign`), not a standalone page.
- **Permanent vs. Flexible assignment types (added 2026-09-18)** — see [[hrm-shift-management-overhaul-plan]] memory for the full design rationale:
  - **`shift_assignments`** table (no migration-less legacy table like `shifts`/`user_shifts` — this one has a real migration) is the append-only source of truth: `type` enum(`permanent`/`flexible`), `start_date`/`end_date` (`end_date` null = open-ended, only legal for `permanent`), `status` enum(`active`/`superseded`/`ended`/`cancelled`), `superseded_by_id` self-referencing chain (no FK, matching the legacy no-FK pattern on `shifts`/`user_shifts`). Never hard-deleted.
  - **`user_shifts` is unchanged in shape** and is now a **generated per-day cache** materialized from `shift_assignments` by `App\Services\Shift\ShiftMaterializer` — every pre-existing direct reader of `user_shifts` (mobile/AI shift-plan endpoints, `CheckMissedCheckIns`, the 3x-duplicated `getUserShiftForDate()`, `TenantShiftResolver` itself) keeps working unmodified. A new nullable `user_shifts.shift_assignment_id` column points back at the source row (null for pre-2026-09-18 rows or a raw single-day `updateUserShift` edit).
  - **Priority rule**: Flexible always wins over Permanent for the dates it covers (the override case — a Flexible assignment is explicitly allowed to be created inside an active Permanent's range); when a Flexible range ends, the user automatically reverts to whichever Permanent is active, with zero manual step. This is enforced **at materialization write time**, not by adding branching logic to `TenantShiftResolver` — `ShiftMaterializer::materializeFlexible()` always overwrites a `user_shifts` row that a Permanent assignment produced, and only respects `override_existing` when the existing row came from *another* Flexible assignment.
  - **Permanent assignments are open-ended and self-maintaining**: `ShiftMaterializer::materializePermanentHorizon()` caches a rolling **120-day horizon** (`ShiftMaterializer::PERMANENT_HORIZON_DAYS`) from an open-ended assignment; the scheduled command `shift:roll-permanent-horizon` (daily, `routes/console.php`) tops every active Permanent assignment's cache back up to `today+120` — this is what removes the need to ever manually re-assign a standing shift (the original pain point this feature solved; the old `assignShift` flow required re-running the same range every ~90 days).
  - **Auto-supersede**: assigning a new Permanent shift to a user who already has one active automatically closes the old one (`end_date = new.start_date - 1`, `status='superseded'`, chained via `superseded_by_id`) — no separate "end it first" step. Explicitly ending one (no replacement) is the "End Permanent Shift" action → `ShiftAssignmentService::endPermanent()`.
  - Service layer: `App\Services\Shift\ShiftAssignmentService` (`assignPermanent`/`assignFlexible`/`endPermanent`, the write path), `ShiftAssignmentValidator` (conflict rules — an overlapping active Flexible needs `override_existing`, same flag/semantics as before this feature), `ShiftMaterializer` (all `user_shifts` writes for this flow — the only class that should write `user_shifts` for assignments going forward).
  - `ShiftController::assignShift` takes a `type` param (`permanent`|`flexible`, default `flexible` for backward compatibility); Permanent skips the 90-day range cap (doesn't apply — it's a single start date) and the `override_existing`/`apply_to_future_only` flags (auto-supersede is implicit). New endpoints: `POST shift.assignment-conflicts` (does this user already have an active Permanent — backs an inline "this will replace X" notice in the assign modal), `POST shift.assignments.{id}.end-permanent`, `GET shift.assignments.history` (full `shift_assignments` history for one user, backs a "History" button on the Existing Assignments tab).
  - **No backfill**: every `user_shifts` row written before this feature has no reliable way to be reconstructed into a `shift_assignments` range (no way to tell "one continuous assignment" from many separate clicks), so none were backfilled — `shift_assignments` starts empty at deploy and only new assignments get real history/type going forward. An employee who was "effectively permanent" via repeated manual reassignment needs one explicit Permanent assignment to start getting the no-reassignment benefit.
  - Consolidated as part of this pass: the two near-duplicate week-off predicates (`ShiftController::isWeekOffOn`/`checkDateIsWeekOff`) now both delegate to `App\Support\WeekOffPredicate::isWeekOff()`. **Not** consolidated (flagged, deferred): the second bulk-assign path `assignBulkShifts` (explicit dates, no week-off handling — stays a separate Flexible-only path from `assignShift`), the 3x-duplicated `getUserShiftForDate()`, the 2x-duplicated mobile/AI `fetchUserShiftData()`/`combineShiftData()`.
  - No `shift`/`shift-settings` module in `config/rbac.php` — routes are gated by plain `role:` + the `shifts.custom` feature middleware only, unlike `branches` (see Org Structure section). Deliberately not addressed as part of the Permanent/Flexible feature (separate, named follow-up).
- **Subscription feature gating (added 2026-09-22)**: two plan keys, `fixed_shift`/`custom_shift`. `EnsureCustomShiftsEnabled` now also requires `feature('custom_shift')` (not just `tenants.custom_shifts_enabled`) — a plan downgrade blocks the Shift/Roster routes even if the column is still on. `ShiftSettingsController` passes `canFixed`/`canCustom` to the settings view; when only one is enabled the Fixed↔Custom mode picker is replaced with a locked notice and a hidden input forcing that mode (`update()` rejects a switch to a disallowed mode). Sidebar's Shift menu checks `custom_shifts_enabled && feature('custom_shift')`. Shift Report tab/card require `feature:fixed_shift,custom_shift` (either).

## Biometric Device Integration (SBXPC bridge)

- Admin UI: `App\Http\Controllers\Settings\BiometricController` (`routes/web.php:568-585`, `role:admin,hr`) — device CRUD, bridge-key generation, config download, enrollment mapping (manual `mapEnrollment` / `autoMap`), roster sync trigger, card assignment, punch reprocessing/listing.
- Bridge-facing API (key-authenticated, `routes/api_v1.php:43-57`): `POST /api/v1/biometric/punches` (`scope:biometric:write`), device heartbeat, enrollment reporting/listing, and a **roster pull/ack protocol**: bridge does `GET /devices/{serial}/roster` to learn desired user diffs and `POST .../roster/ack` to confirm what it wrote to the terminal. Punch persistence (dedupe + enroll self-map + `ProcessBiometricPunch` dispatch) lives in `App\Services\Biometric\BiometricPunchIngestService::ingest()`, shared with the FkWeb receiver below.
- **FkWeb direct push — no bridge (added 2026-09-28)**: terminals set to server-client mode `FkWeb` POST straight to `POST /api/v1/biometric/fkweb/{push_token}` (`App\Http\Controllers\Api\V1\BiometricFkWebController`, outside `apiv1`/`apikey`, `throttle:biometric-push`). Auth = the per-device secret `biometric_devices.push_token` in the path (the device cannot send auth headers) + `dev_id` header must equal `serial_number`. Admin gets/rotates the URL via the link icon on `/settings/biometric` (`BiometricController::pushUrl`, `POST settings/biometric/devices/{device}/push-url`); base origin = `config('biometric.fkweb.base_url')` (`BIOMETRIC_PUSH_BASE_URL`, defaults to `APP_URL` with https→http). Protocol (verified on firmware M61BH v3.16.1842): HTTP/1.0 POST, headers `request_code`/`dev_id`/`trans_id`/`blk_no`, body = 4-byte LE JSON length + JSON + binary; reply is headers only (`response_code`, `trans_id`, **`Content-Length: 0` — without it the device never sends punches**). `receive_cmd` (~10s heartbeat → `ERROR_NO_CMD`, updates `last_seen_at`/`model`), `realtime_glog` (`{user_id:"00000015",verify_mode,io_mode,io_time:"YmdHis"}` → one punch via `BiometricPunchIngestService`; `OK` only after it is persisted, so the device keeps and resends on error; zero-padded `user_id` → `enroll_no` "15"; `io_time` is device-local wall time like the bridge's), `realtime_enroll_data` (user + FP/face templates in 1 KB blocks; block 1's JSON links/creates the `biometric_enrollments` row, templates are discarded, never stored). Because nginx/Apache+FPM drop headers containing `_`, a missing `request_code` is inferred from the body shape. Deployment constraints: the device speaks **plain HTTP only** (no TLS, IP rather than hostname is safest) — the push URL must not redirect to https; `verify_mode` codes (seen 2, 10) are not yet mapped to a method (`config('biometric.fkweb.verify_mode_methods')`, empty → `attendance_type` stays `fingerprint`); `io_mode` is stored in `payload` but not used for direction.
- `App\Services\Biometric\BiometricRosterService::rebuild()`: **key rule** — the device's `enroll_no` is always `(string) users.id` (never hand-mapped), so punch ingestion resolves straight back to the employee; computes `pending`/`removing`/`targets` diff per device.
- `App\Services\Biometric\BiometricAttendanceService::apply()`: turns one `biometric_punches` row (`status = pending`) into an `attendances` write, routed through `AttendanceEntryService` (which enforces period lock, audit trail, domain event, summary refresh) — described as "a straight lift of the retired ProcessFingerprintPunch" job, i.e. this replaced an older CAMS-based pipeline (consistent with `hrm-biometric-integration` memory). Since 2026-09-23, this method branches on `tenants.allow_multiple_punches`: `=0` tenants (default) keep this exact single-pair-fold behaviour (a 3rd+ punch in a day is skipped, not stored as a new session); `=1` tenants route instead through `AttendancePunchService::capture()` — the same multi-punch funnel mobile/web/manual punches use — so additional punches open new sessions. See "Attendance — multiple punches per day" above.
- Models: `BiometricDevice`, `BiometricEnrollment`, `BiometricPunch`.
- **Subscription feature gating (added 2026-09-22)**: new plan key `attendance_biometric` (default off, paid add-on — previously this whole section had no plan gate at all, only `role:admin,hr`). `BiometricController`'s routes are wrapped in `feature:attendance_biometric`; the sidebar "Biometric Terminals" link is wrapped in `@feature('attendance_biometric')`.
- **Live-updating Punches page (added 2026-09-22)**: `settings/biometric/punches` polls itself every ~7s via AJAX (`Accept: application/json`); `BiometricController::punches()` branches on `wantsJson()` and returns the rendered `partials/_punch-rows.blade.php` fragment + pagination HTML instead of a full page. The poll never touches the search input while it has focus and guards against overlapping in-flight requests.
- **Direct device-side onboarding (added 2026-09-22)** — per-device opt-in, `biometric_devices.allow_direct_onboarding` (default `false`). When true, a device-reported enrollment (`BiometricV1Controller::reportEnrollments()`) with no matching HRM user auto-creates one via `App\Services\Biometric\BiometricEmployeeProvisioningService::createFromDeviceEnrollment()`:
  - Employee-count cap checked first via `App\Services\EmployeeCapService::canCreateEmployee()` (`tenants.max_employees`, overridden by `tenant_subscriptions.max_employees_override` when an `active`/`trial` row exists — no `TenantSubscription` model exists in this app, read via raw query). Over cap → no user created, the enrollment row's `last_error` is set instead (same unmapped shape as today, just with a reason).
  - Password is the literal `12345678`, hashed; `users.must_change_password` (new column) is set `true` — **tracked but not enforced anywhere** (no forced-password-change middleware/UI exists in this app; follow-up).
  - Email is generated as `{tenant subdomain}.{slug(name)}{new user id}@gmail.com` (two-step: placeholder unique email at create, real one right after, since `users.email` is `NOT NULL` UNIQUE and the rule needs the new id) — numeric-suffix retry on collision.
  - Only a `User` + one `UserJobDetail` row are created (not the full `UserBasicDetail`/`UserLocation` set `EmployeeProvisioningService::hire()` creates) — HR fills the rest in later via the existing Edit Employee drawer.
  - The resulting `BiometricEnrollment` row deliberately keeps the device's **original** `enroll_no` (not `(string) users.id`) and is stored `source='manual'`, `sync_state='synced'` — this is a legacy-hand-map-style row on purpose, so `BiometricRosterService::rebuild()`/`syncUser()` never try to also create a second, `(string)id`-keyed identity for the same person on the same device. A new private `alreadyOnDeviceUnderOtherEnroll()` check in that service enforces this. `BiometricRosterObserver::created()`/`updated()` are explicitly suppressed (`BiometricRosterObserver::suppressed()`) while the User is being created, since the triggering enrollment row isn't linked to the new user yet at that point — `reportEnrollments()` calls `BiometricRosterService::syncUser()` itself right after linking, so the new employee still gets auto-provisioned onto any *other* devices in the tenant normally.
  - Also applies to FkWeb direct push (2026-09-29): `BiometricFkWebController::onboard()` runs the same service from a `realtime_enroll_data` block 1 (`user_name` → employee name). That route has no auth middleware, so it binds `current_tenant` to the device's tenant around the call (TenantTrait stamps `tenant_id` from it). It also fires for an existing still-unmapped row when the device re-sends it; a linked row never creates a second employee.
  - **Follow-up, not yet done**: `EmployeeCapService` is not wired into the regular manual Add-Employee flow (that flow still has zero seat-cap enforcement).
- **Push to Device (added 2026-09-22)** — `App\Services\Biometric\BiometricRosterService::pushToDevice(BiometricDevice $device, iterable $users)`: immediately flags the given users `pending` for the given device, regardless of that device's `auto_provision` setting (unlike `syncUser()`, which only touches `auto_provision=true` devices). Exposed on the Employees list (`resources/views/client/user/view-user.blade.php`) as a bulk-select action reusing the existing Location-Tracking checkbox column/bulk bar, gated by `POST employee/bulk-push-to-device` → `UserController::bulkPushToDevice()`, itself gated `feature:attendance_biometric`. Still only *marks* the DB state pending — no on-demand device write exists; the bridge applies it on its next poll cycle (honest ~1 min framing in the UI, not an instant-push promise).
- **Known gap, not fixed by any of the above**: `biometric_enrollments.card_pushed` is referenced in code (`rosterAck()`, `BiometricRosterService`) but was never actually added by any migration — reads/writes to it silently no-op rather than erroring.

## Field Tracking (GPS, paid add-on)

- Settings UI: `App\Http\Controllers\Settings\FieldTrackingController` (`role:admin,hr`) — **seat count and the on/off master switch are vendor/billing-owned and read-only here**; the tenant admin can only adjust ping cadence (`field_tracking_ping_seconds`) and retention (`field_tracking_retention_days`, floored by `config('location.retention_floor_days')`, default 30). Saving requires the `field.tracking` middleware (`EnsureFieldTrackingEnabled`) in addition to the page itself always being reachable so the upsell message can render when off.
- `App\Services\FieldTracking\FieldTrackingService` is the **single source of truth** for seat rules, explicitly shared between the web employee list (bulk/single toggle in `UserController`) and the mobile clock-in path so entitlement logic can't drift between the two. `seatsUsed()` counts **every** user with `user_job_details.location_tracking_enabled = 1`, regardless of `users.status` (active or inactive) — a deactivated employee still holds their seat until tracking is explicitly turned off for them; `seatsPurchased()` reads `tenant.field_tracking_seats`. (Prior to 2026-09-23 `seatsUsed()` only counted active users, which let an admin deactivate a tracked employee to silently free their seat — without ever clearing the flag — assign it elsewhere, then reactivate the original employee to exceed the purchased cap; counting regardless of status closes that at the root instead of guarding each status-changing endpoint individually.)
- GPS breadcrumbs (as of 2026-10-01) land in the two-table `attendance_tracking_sessions`/`attendance_tracking_points` schema via the mobile `track`/`track-batch` endpoints (`Api\Attendance\AttendanceController`, throttled `location-ingest`) — replaces the old flat `attendance_tracks` table, which is now legacy/frozen (kept read-only for one release cycle, still `field-tracking:prune`-managed, before removal). Usage rollups in `field_tracking_usage` now count `attendance_tracking_points` rows (per `docs/database.md`).
- **Session = one clock-in→clock-out punch pair, not one day.** `App\Services\FieldTracking\TrackingSessionService::onPunchCaptured()` opens a session on every punch `in` and closes it on the paired `out`, hooked into `AttendancePunchService::capture()` — so a multi-punch tenant's lunch-break cycle gets its own session row with its own separated breadcrumb trail, fixing the old table's inability to tell two same-day cycles apart. `AttendanceRollupService::recompute()` backfills each session's `attendance_id` after writing the day's rollup row (used only by the 4 legacy `attendance_id`-keyed read views — `todayLocations`, the admin map view, and the two profile "today's trail" spots — all rewritten to query through `AttendanceTrackingPoint::forAttendanceId()`, same response shape).
- `App\Services\FieldTracking\TrackingPointIngestService::ingestBatch()` is the ingest path both `trackBatch` and `trackLocation` (now a 1-point batch internally, server-minted `point_id`) call. Points carry an optional client-sent `point_id` (when omitted the server derives `sha1(lat|long|track_time)`, coords at 7 decimals + epoch second, so retries still dedupe); the DB unique constraint `(tenant_id,session_id,point_id)` plus `insertOrIgnore` (chunked 500, matching `RecordLocationPings`' existing shape) makes a retried batch idempotent by construction — no manual per-row dedup check. A batch is resolved against the caller's open session, or a session closed within `config('location.late_point_grace_minutes')` (default 15) of "now" — a point whose own `track_time` is after that session's `ended_at` is rejected even inside the window. `field-tracking:sweep-sessions` (scheduled daily) force-closes sessions left open with no activity past `--stale-hours` (default 18) and prunes (archives to NDJSON, then deletes) points/sessions past each tenant's retention window — the two-table sibling of `field-tracking:prune`, which keeps running against the old `attendance_tracks` table unchanged until it's removed.

- **Three `requirement_type`s with different approval behavior** (`ExpenseController::updateStatus`, `app/Http/Controllers/Expense/ExpenseController.php:727`):
  - `advance` — approving only marks `status=approved`; balance is credited separately when a *payment* is created (`PaymentController`).
  - `settlement` — approving runs `handleSettlementApproval()`, which deducts the balance immediately inside the same transaction; a caught exception rolls back and surfaces the real error message to the caller.
  - `reimbursement` — approving marks `status=approved`; actual reimbursement happens when a payment is later processed.
  - Only `pending` expenses can be decided; ownership is checked via `scopeCoversOwner()`, replacing a prior bug where the manager-ownership check was unreachable dead code and any manager could approve any employee's expense.
  - **Approve/reject is one shared implementation** — `App\Services\Expense\ExpenseService::decide()` — used by both the web panel and the mobile API (previously two copy-pasted controllers). It locks the expense row (and a settlement's balance row) `FOR UPDATE` and re-checks `pending` *after* the lock, so a double approval can't double-deduct. Accepted decisions are `approved`/`cancelled` only; the old manual `complete` action was removed (it only worked from `pending`, bypassed approval/payment, and wrote columns that never existed) — an expense now becomes `complete` automatically when it is fully paid.

## Asset Management (2026-09-22)

Full asset lifecycle module — categories/types, registration with a system-generated Asset ID, purchase/warranty/vendor/branch detail (all nullable except the core identity/status fields), employee assignment with **blocking acceptance**, return, transfer, repair, damage/loss, retirement, and disposal. New tables: see `docs/database.md`'s "Assets" section.

- **State machine, not `ApprovalService`**: transfer/disposal are direct actions gated by RBAC permission (not a second approver) — deliberately not built on the generic multi-level `ApprovalService` (§ "Approvals" below), which is purpose-built for hierarchical manager-approval chains, not a multi-branch custody state machine. `app/Services/Asset/AssetLifecycleService.php` is the single choke point for every transition (`register`/`assign`/`accept`/`returnAsset`/`transfer`/`sendForRepair`/`completeRepair`/`reportDamageOrLost`/`resolveDamageReport`/`retire`/`dispose`); each method validates the legal transition from the asset's current status, writes one `asset_histories` row, calls `AuditLogger::record('tenant_user', ...)`, and fires `AssetNotificationService` — the same "domain history + audit log + notification" triple-write pattern the Requests module uses.
- **Acceptance is blocking**: `assign()`/`transfer()` put the asset into `pending_acceptance` and leave `assets.current_assignee_id` null; only `accept()` (by the assignee, or an admin/HR "force accept", logged as `ACCEPTANCE_FORCED`) moves it to `assigned` and sets `current_assignee_id`. A transfer re-enters `pending_acceptance` for the new holder — it does not skip the acceptance gate.
- **Repair doesn't end an assignment**: sending an assigned asset for repair flips `assets.status` to `in_repair` (remembering the prior status in `pre_repair_status`) without touching the active `asset_assignments` row — the same employee gets the same asset back on completion.
- Controllers, `app/Http/Controllers/Asset/`: `AssetController` (register/list/detail/edit/delete, bulk status/category/branch update, CSV export, employee self-service `myAssets`/`myAssetShow`), `AssetLifecycleController` (one thin action per transition — mirrors `TeamController::markAttendance()`'s wrapper shape), `AssetCategoryController`/`AssetTypeController`/`VendorController` (small reference-data CRUD, mirror `BranchController`), `AssetAttachmentController` (mirrors `ProjectController::storeAttachment()`: files via `FileStorageService` module `asset_attachment` — see `docs/file-storage.md`).
- **Ownership bypass for accept/return**: an employee may always accept/return an asset currently assigned to them (`AssetAssignment.user_id === auth()->id()`), independent of the coarse `assets` RBAC grant — same "everyone can act on their own record" pattern as Loans/Requests. Routes: `routes/web.php` `assets.*`/`asset-categories.*`/`asset-types.*`/`asset-vendors.*`/`my-assets.*`, each gated `permission:assets,{view|create|edit|delete|manage}`.
- **RBAC** (`config/rbac.php`, module `assets`): `admin`/`hr` → `'all'`; `manager` → `['view' => 'team']` (read-only, scoped via `User::managedBy()` against `current_assignee_id`); `employee` → `['view' => 'own']`.

## Offboarding

Rebuilt 2026-09-30 (was dummy-data/manual-only). Full flow: submit -> approval (via `ApprovalService`) -> knowledge transfer -> clearance -> exit interview -> final settlement -> complete. Service layer under `app/Services/Offboarding/`; controllers (`app/Http/Controllers/offboarding/OffboardingController.php` web, `app/Http/Controllers/Api/Offboarding/offboardingController.php` mobile-employee-only) are thin HTTP glue over it.

Key methods: `submit()`, `decide()`, `startKnowledgeTransfer()`/`completeKnowledgeTransfer()`, `startClearance()`/`completeClearanceTask()`, `recordExitInterview()`/`skipExitInterview()`, `requestNoticeOverride()`/`decideNoticeOverride()`, `cancel()`, `reopenStage()`, `complete()` (moved employee deactivation + `UserJobDetail.leaving_date` stamping here, at actual completion — previously it fired prematurely at HR-approval time).

- **Final settlement**: `offboarding_settlement_items`, a computed worksheet built by `App\Services\Offboarding\OffboardingSettlementService::generateWorksheet()` (called when the exit-interview stage resolves) — auto-generates lines for pending salary, leave encashment (`leave_types.is_encashable`), one line per outstanding `Loan` (skipped entirely if the tenant's `loan_management` feature is off), expense advance/reimbursement balances (skipped if `expense_management` is off), and a notice-period-shortfall deduction (skipped if an approved `waiver` override exists). Each line has `computed_amount` (system value, never overwritten) and an optional `override_amount`; regenerating the worksheet preserves any line HR already overrode. Severance/custom lines are always manual (`addManualLine()`) — deliberately not auto-formula'd.

Don't write to these mirror columns directly from new code.
- **Permissions**: `permission:offboarding,{view|create|approve|edit}` middleware + `feature:offboarding` now actually gate every route (previously zero route-level enforcement despite both being defined in `config/rbac.php`/`config/features.php`). `config/rbac.php` gained scoped grants for `manager` (`view`/`approve` => `team`) and `employee` (`view`/`create` => `own`) — `edit` (clearance/KT/settlement mutation) stays admin/hr-only.

- **Daily scoring** (`App\Services\Performance\PerformanceDailyScorer::scoreDay()`): reuses `App\Services\Attendance\AttendanceDayResolver` — the app's own canonical day-classifier — instead of re-deriving attendance state, so attendance-policy changes (grace, present/half-day ratios) are honoured automatically and there's no dependency on `attendance_summaries`' cache freshness. Every query is tenant-safe (`withoutGlobalScopes()` + explicit `tenant_id`, matching `AttendanceEntryService`'s established pattern — this fixed a real cross-tenant `Holiday` leak in the old service). Five components, each independently nullable (excluded from the day's blend, never scored as 0, when genuinely inapplicable — e.g. a holiday, zero tasks assigned, no regularization that day): attendance (late/early-departure penalties folded in), task completion, task on-time (reuses `Task::scopeOverdue()`'s exact definition for an overdue penalty), project participation (derived from task activity scoped to the employee's active `project_assigns` — no separate per-project effort table), and regularization (penalty now differs by approved/rejected/pending outcome — the old service penalized all three identically).
- **The one canonical formula**: `App\Services\Performance\PerformanceScoreCalculator::blend()`/`grade()` — every weighted average and letter grade in this module goes through this single class. It excludes a component only when its value is PHP `null`, never for a legitimate `0.0`, and renormalizes the remaining weights to 100%. 10-band grade scale (A+ down to F). This replaced **four** independent, mutually-inconsistent implementations that used to disagree with each other (`PerformanceCalculationService::calculateOverallScore()` — an unweighted mean despite its docblock; `EmployeeKpiScore::getOverallScoreAttribute()` and `PerformanceController::calculateOverallScore()` — both a weighted 35/35/15/5/10 average but with a truthiness bug, `if ($score > 0)`, that wrongly excluded legitimate zero scores; `ManagerPerformanceReviewController::recalculateOverallScore()` — yet another formula with a different 6-band grade scale, so the same stored score could earn a different letter grade depending which code path last touched it).
- **Rollup, not independent recalculation**: `App\Services\Performance\PerformanceRollupService::rollupMonth()` averages a month's *already-calculated* `employee_daily_performance` rows (excluding `excluded`/`pending`/`failed` ones from both the numerator and denominator) into `employee_kpi_scores` — the monthly table no longer computes anything from raw attendance/task data itself. `weekly()` does the same over 7 days, on demand, never persisted (no weekly table, matching `attendances`/`attendance_summaries` having none either). Manager rating is blended in at the monthly level only (`objective_score` + `manager_rating_score` via the same `blend()`), and is **excluded and renormalized away**, not zeroed, whenever no `submitted` review exists yet for the month — `employee_kpi_scores.manager_rating_included` records whether it was actually counted.
- **Tenant-configurable weights**: `performance_policies` (mirrors `attendance_policies` — nullable-tenant global default, versioned by `effective_from`), resolved via `App\Services\Performance\PerformancePolicyResolver` (line-for-line mirror of `App\Services\Attendance\PolicyResolver`, `$tenantId` always passed explicitly — safe from a scheduled console command where `current_tenant` is unbound).
- **Scheduling** (`routes/console.php`): `performance:calculate-daily` (`App\Console\Commands\CalculateDailyPerformance`) runs `dailyAt('02:30')` — 90 min after `attendance:update-summaries`' `01:00`, so yesterday's attendance data has settled — scoring yesterday by default, `--date`/`--from`/`--to`/`--user`/`--force`/`--dry-run` for bounded backfills. `performance:rollup-monthly` (`App\Console\Commands\RollupMonthlyPerformance`) runs `monthlyOn(1, '03:00')`, after a full month of daily rows exists. Both skip users with no/invalid `tenant_id` (there is real leftover test-fixture data in this DB with `tenant_id = NULL` — e.g. a "Legacy Removal Test User" — that would otherwise fail the `employee_kpi_scores.tenant_id` foreign key). Both replaced the old `performance:calculate` command (monthly-only, no `withoutOverlapping()`, computed everything from scratch itself).
- **On-demand path**: `PerformanceController::individualReport()` on a KPI-score cache-miss calls `rollupMonth()` under a short `Cache::lock()` (aggregating already-precomputed daily rows, not re-deriving from raw data) instead of the old inline calculate-then-`create()`, which could race on the `(user_id,reporting_month)` unique key and 500.
- **Deleted**: `PerformanceCalculationService` (fully superseded), `CalculateMonthlyPerformance` command, `PerformanceController::performanceComparison()`/`submitManagerRating()` (confirmed unreachable — no routes referenced them), `ManagerPerformanceReviewController::getPerformanceSummary()` (confirmed dead code), the orphaned `employee-search.blade.php` view and the `team/export` route that pointed at a nonexistent `employeeSearch()` method (was a guaranteed 500 if ever hit).

Route-level `permission:performance,{action}` / `permission:performance_reviews,{action}` middleware added (previously auth-only, all enforcement in-controller, inconsistent with sibling modules like `overtime`/`recruitment`).

- `App\Http\Controllers\Attendance\RequestController` (web) — self-service `index`/`store`/`update`/`destroy` (soft-cancel, see below), attachment delete/download, stats, export; manager surface at `manager/requests*` (`managerIndex`/`managerShow`/`approve`/`reject`/`bulkApprove`/`managerExport`/`managerStats`). `App\Http\Controllers\Api\Attendance\RequestController` (mobile, `Api\Attendance` namespace despite having nothing to do with clock-in/out) mirrors the same capability set: `type`/`store`/`view`/`view_all`/`updateStatus`/`show`/`update`/`cancel`.
- **RBAC is now consistently enforced on both surfaces** (2026-09-17 pass) via `config('rbac.php')`'s `requests` module matrix (`admin`/`hr` → `all`, `manager` → `['view' => 'team', 'approve' => 'team']`, `employee` → `['view' => 'own']`) and the shared `AuthorizesByScope` trait (`applyScope()` for list queries, `scopeCoversOwner()` for single-record checks) — previously the web controller used ad hoc `$user->role == 'admin'` checks that silently ignored any custom role's `requests` grant, while the mobile controller already did this correctly; both now match. - **Overlap rule** (`Request::scopeOverlapping()` on the model, shared by web `store()`/`update()` and mobile `store()`/`update()`): a new/edited request is rejected if the user already has a `PENDING` or `APPROVED` request whose date range overlaps (start/end/containment all checked) the new one — extracted to one model scope so the rule can't drift between web and mobile.
- Attachments are stored through `FileStorageService` (module `request`, folder `uploads/requests/{tenant}` — see `docs/file-storage.md`) on both surfaces and both store/update; older rows keep their `uploads/requests/attachments/...` paths. `requests.download-attachment` (web) streams the file as a real download via `FileStorageService::stream()` rather than relying on a raw public URL.
- Every state-changing action (create/update/cancel/approve/reject) now also calls the shared `AuditLogger::record()` (actor_type `'tenant_user'`, action strings `requests.created`/`.updated`/`.cancelled`/`.approved`/`.rejected`) in addition to the module's own `request_histories` trail — previously this module had no `AuditLogger` coverage at all.
- Notifications (`RequestNotificationService`): `notifyRequestSubmitted`/`notifyRequestApproved`/`notifyRequestRejected`/`notifyRequestCancelled`, all dual-channel (FCM + DB `notifications`). Now wired into every relevant action on both web and mobile — previously mobile never called this service at all, web's `reject()` had a dead `// TODO`, and `bulkApprove()` sent nothing.
- Status vocabulary is upper-case here: `PENDING`, `APPROVED`, `REJECTED`, `CANCELLED` (distinct from Leave's lower-case `pending`/`approved`/`cancelled` — don't assume the two modules share a status enum).
- `request_types` table defines the type catalog (WFH/Travel per `docs/database.md`); `RequestType` model.
- `daily_reports`/`DailyReport` (WFH daily work-log table) has no controller or route anywhere referencing it — intentionally left dormant/unimplemented, not a bug.
- Not integrated with the generic `ApprovalService` multi-level workflow engine (no `requests` handler registered) — this module remains single-approver only; a future enhancement, not planned here.
- **Subscription feature gating (added 2026-09-22, manager routes fixed same day)**: the self-service `requests.*` route group, its sidebar entry ("Travel & WFH") and the Leave Report's WFH & Travel card require `feature:wfh_travel`. The manager-facing `manager/requests*`/`manager/stats` routes (`managerIndex`/`managerShow`/`approve`/`reject`/`bulkApprove`/`managerExport`/`managerStats`) are declared as standalone routes outside the `requests.` prefix group, so they were initially missed by the group-level gate — a tenant with the feature disabled could still reach the manager approval screen directly by URL even though the self-service side and the sidebar link were correctly blocked/hidden. ## Notifications

- In-app: `notifications` table (Laravel's built-in), `App\Http\Controllers\Api\Notification\NotificationController` (index, unread-count, mark read/all-read, destroy/destroy-all) — **mobile only**; there was no web-panel notification UI at all until the Broadcast Notification module (below) added one.
- Push: `App\Services\FirebaseService` (FCM), tokens managed via `App\Http\Controllers\Api\FCM\FCMController` (`store`/`remove` token) and stored on `users.fcm_tokens` (JSON) per `docs/database.md`. `App\Channels\FcmChannel` is the proper Laravel notification-channel wrapper around it (reads `fcm_tokens`, auto-prunes dead tokens on send) — opt in via a Notification class's `via()` returning `[..., FcmChannel::class]` + implementing `toFcm($notifiable): ['title','body','data'=>[...]]`. Several older `*NotificationService` classes (e.g. `AnnouncementNotificationService`) instead hand-roll their own per-user `fcm_tokens` loop calling `FirebaseService` directly, duplicating what `FcmChannel` already does — an existing inconsistency, not a pattern to copy in new code (the Broadcast module below uses `FcmChannel` via `via()`, matching `ApprovalService`'s cleaner `Notification::send()` shape).
- Email: SMTP (Hostinger, per prior memory), used for recruitment pipeline mail and presumably payslip/report mail (verify `App\Mail\*` before assuming coverage).
- **Content rules (audit 2026-09-29)** — every `*NotificationService` sends a push and a database notification; the stored `title`/`message` must be the **same wording** as the push (pass them into the Notification class — see `LeaveStatusChangedNotification`, `LeaveSubmittedNotification`, `AttendanceNotification`, `TaskStatusUpdateNotification`, which accept `$title, $message`). Wording follows the real status (`LeaveNotificationService::message()` — approved / rejected / **cancelled** for a revoked approved leave via `notifyLeaveCancelled()`; days from `leaves.total_days`, else the inclusive start..end span). Recipient lists (`getUsersByRole($role, $tenantId)` in the Leave/Attendance/Request/Overtime/Regularization/Expense services) filter `tenant_id` explicitly and drop the subject employee (an HR/admin applying or clocking in isn't notified about themselves). Clock-in/out pass the captured `attendance_punches` row (`notifyClockIn/Out($attendance, $user, $punch)`) so a 2nd session reports its own time ("clocked in again at … (session 2)"), not the day's first punch. Channel strings: never `'fcm'` (no such driver) — use `FcmChannel::class`; `MissedCheckInNotification` does, and accepts the user id `CheckMissedCheckIns` passes; `LocationStatusNotification` is database-only because `LocationAlertService` pushes itself. `ApprovalService::notifyRequester()` skips `leave`/`overtime`/`regularization` (their handlers send the specific notification; `RegularizationApprovalHandler` now does too) so a workflow decision isn't announced twice.
- **Missed check-in alert** — `attendance:check-missed-checkins` (scheduled every 5 min in `routes/console.php`; needs the server cron `php artisan schedule:run` every minute). For each `user_shifts` row with `status=upcoming` (plus synthesised rows for fixed-shift tenants) with no `attendances.clock_in` once `shift start + shifts.grace_minutes` has passed, sends one `MissedCheckInNotification` (push + in-app) to the **employee**, their **reporting heads** (`user_reporting_heads` — the "manager"), and the tenant's **HR** and **admin** users; not every `manager`-role user. Skipped (`notExpectedReason()`): approved leave covering the shift start (a leave starting `session2` that day still expects a morning clock-in), an active `holidays` row covering the date, or a `user_weekoffs` week-off (`WeekOffPredicate`). Once per shift per day (`user_shifts.missed_checkin_notified`, cache key for fixed shifts).
- **Payroll notifications** — `PayrollNotificationService` (push + `CustomNotification`, `type=payroll`) tells the **employee** about their own payslip on a real `payment_status` change only (`statusMessage($payroll, $old, $new)`): → `processed` "📄 Payslip Ready" (net pay), → `paid` "💰 Salary Credited" (date / mode / ref), a visible (processed/paid) slip reopened → "✏️ Payslip Under Correction", cancelled → "🚫 Payslip Cancelled"; same status, paid→processed and pending→cancelled send nothing. Wired in `MonthlyPayrollController::updateStatus`, `reopen`, and `bulkUpdate` (bulk sends after the response via `dispatch(...)->afterResponse()`). Also "🎉 Bonus Approved" (`notifyBonusApproved`, workflow handler + no-workflow paths in `PayrollBonusController`) and "📈 Salary Revised" (`notifyRevisionApplied`, skipped for `revision_type=initial`; handler + both no-workflow paths), sent `DB::afterCommit`.

## Broadcast Notifications (2026-09-25)

Targeted, audience-filterable in-app notifications — the thing `announcements` (always "every active tenant user", no filtering) and the Reports module's ad hoc `getUserIdsForAssignment()`-style single-`assign_type` pickers (Branch/Shift assignment) couldn't do. Built as **one shared schema + one shared delivery mechanism**, written to directly by both this app (Tenant Admin composer) and the separate `hrm-superadmin` app (Superadmin composer, cross-tenant). No HTTP bridge between the two apps for delivery — `hrm-superadmin` gets a plain unscoped Eloquent model over the same tables, the same pattern it already uses for `Tenant`/`User`/`Role`. **All 4 phases are done** (Tenant Admin composer + audience resolver + web notification center; queue-based delivery + scheduled/expiry commands; Superadmin composer + 5 cross-tenant audience modes; email/push/SMS channel selection).

### Phase D — channel selection (push/email/SMS), Tenant Admin composer only

- **Scope decision**: Phase D only touches the **Tenant Admin composer** (`hrm (3)`). `hrm-superadmin`'s composer keeps `channels=['database']` only, same as its existing "no FCM push, no `FirebaseService`/credentials here" boundary from Phase C — sending tenant-facing email/SMS from the superadmin app would need its own duplicate SMTP/Airtel credentials wired into a separate app, which is out of scope here and not requested.
- **`channels[]`** is now a real composer field (checkboxes: Push/Email/SMS; "In-app" is always-on and not a checkbox) validated in `BroadcastComposerService::validate()` (`in:fcm,email,sms`) and merged with the implicit `'database'` entry before the `Broadcast` row is created. **Before this phase, every broadcast's `channels` was hardcoded to `['database']`** — `App\Notifications\BroadcastNotification::via()`'s FCM-gating branch existed since Phase A but was structurally unreachable until now (nothing ever set `channels` to include `'fcm'`). Verified backward-compatible: a broadcast created with no `channels` selected still resolves `via()` to exactly `['database']`, matching every broadcast created in Phases A–C.
- **Email**: `BroadcastNotification::toMail()` — stock `MailMessage` (subject/greeting/line/optional action button), gated into `via()` via the plain Laravel `'mail'` channel string when `channels` contains `'email'`. No new mail infrastructure — reuses the same SMTP config (`docs/database.md`/prior memory: Hostinger) every other `*Notification::toMail()` in this app already uses.
- **Push**: unchanged from Phase A (`App\Channels\FcmChannel`), now actually reachable for the first time (see above).
- **SMS — real regulatory constraint, not just a missing integration**: `App\Channels\SmsChannel` wraps the same Airtel IQ gateway OTP login already uses (`Api\Auth\AuthController`), but with its **own** `sms.airtel.broadcast_dlt_template_id` config key (env `DLT_TEMPLATE_ID_BROADCAST`), deliberately separate from `dlt_template_id` (the OTP template). **Indian DLT regulations require every SMS to match a pre-registered, approved template** — an admin-authored free-text broadcast body cannot legally be sent through this gateway using the OTP template, and no "broadcast" template is registered yet. Left unconfigured by default: `SmsChannel` gracefully no-ops (logs at `info` level, never throws) exactly like `FirebaseService::isReady()` degrades on missing FCM credentials — verified via a direct `SmsChannel::send()` call with no template configured, confirmed no exception and the expected log line. The composer UI shows the SMS checkbox **disabled** with an explanatory tooltip rather than hidden, so it's discoverable but not falsely usable. **This is the one piece of Phase D that needs a manual, non-code step (registering a DLT template with Airtel and setting the env var) before it does anything** — not a bug, not incomplete code.
- **Verified**: `via()` correctly gates all 4 channel combinations against a live `Broadcast` model; `toMail()`/`toSms()`/`toFcm()` all produce correct content; a full compose→queue→deliver run with `channels=['fcm']` selected completed successfully end to end. **Disclosed side effect from that FCM verification run**: real Firebase credentials are configured in this dev environment (`storage/app/firebase/firebase_credentials.json`), so the test made real Firebase API calls for 3 test users' stored device tokens — all were stale/unregistered and got pruned by `FcmChannel`'s existing dead-token cleanup (no push was actually delivered to any live device; pruning stale tokens is that channel's normal, intended behavior). No SMS or email verification run was performed live (SMS is inert by config; a live email send would have gone out via real SMTP to whatever address a test user's `email` column holds, so that path was verified by inspecting the built `MailMessage` object only, never dispatched).

### Phase C — Superadmin composer (`hrm-superadmin`, cross-tenant)

- **Models** (`hrm-superadmin/app/Models/Broadcast.php`, `BroadcastRecipient.php`): plain, unscoped, same table names as hrm (3)'s — no migration on this side (this panel never migrates the shared DB).
- **Audience resolver** (`hrm-superadmin/app/Services/Broadcast/SuperAdminBroadcastAudienceResolver.php`): 5 modes collapsing into 2 query primitives (`superAdminsQuery()`/`tenantUsersQuery()`) — `superadmin_users` (optional role narrowing among superadmin/support/billing), `tenant_admins_managers` (role IN admin/manager/**hr** — `hr` bucketed here per the confirmed product decision — optional `tenant_ids[]` narrowing), `tenant_employees` (role=employee, optional `tenant_ids[]`), `selected_tenants` (`tenant_ids[]` required, optional role narrowing — deliberately the same query primitive as the two modes above, just tenant-first instead of role-first), `all_eligible` (union of all 3 unfiltered — highest blast radius, gated **both** by route middleware (`sa_role:superadmin,support` on the composer generally) **and** a service-layer check in `BroadcastComposerService::applyAudienceRules()` that hard-rejects it unless the actor's `role` is exactly `superadmin`, since the broader route gate alone would let `support` through). All 5 modes' counts verified against live cross-tenant data (e.g. `tenant_admins_managers` scoped to one tenant matched the sum of that tenant's admin+manager+hr users exactly, cross-checked against Phase A's own resolver output for the same tenant).
- **Composer orchestration** (`hrm-superadmin/app/Services/Broadcast/BroadcastComposerService.php`): mirrors hrm (3)'s class/method names (`validate()`/`validateAudienceOnly()`/`countRecipients()`/`create()`/`snapshotRecipients()`) but is necessarily separate code — no shared-package mechanism between these two Laravel installs (same precedent as the hand-synced `config/features.php` duplicate). **No scheduling here** — every superadmin broadcast sends immediately, `scheduled_at` stays null; this is a deliberate scope decision (only the Tenant Admin composer supports "schedule for later").
- **Delivery, direct shared-table writes, no HTTP bridge** (`hrm-superadmin/app/Services/Broadcast/BroadcastDeliveryService.php`): for `recipient_type=tenant_user` rows, inserts directly into the shared `notifications` table with the exact JSON shape (`title`/`message`/`type` keys) and exact `type` string (`App\Notifications\BroadcastNotification`) hrm (3)'s own Notification class produces — verified end-to-end that a broadcast composed in `hrm-superadmin` is immediately visible via hrm (3)'s own `$user->notifications()` relation (mobile API, unmodified) **and** hrm (3)'s web bell (which reads `broadcast_recipients` directly, correctly tenant-scoped to the recipient's own `tenant_id`, not the composer's). No FCM push from this app (no `FirebaseService`/credentials here) — `channels` is always `['database']` for superadmin broadcasts. For `recipient_type=super_admin` rows, no external table write — this panel's own notification bell reads `broadcast_recipients` directly (see below), so the snapshot row alone suffices.
- **`tenant_id` sentinel for super-admin recipients**: `broadcast_recipients.tenant_id` is NOT NULL (Phase A's schema decision), and a super admin isn't tenant data, so those rows store `tenant_id=0` — a documented sentinel, inert by construction since no query ever scopes a super-admin-recipient lookup by `tenant_id` (always `recipient_type='super_admin' AND super_admin_id=X` instead). Verified via smoke test.
- **Queue segregation — a real bug caught and fixed during this phase**: both apps' delivery jobs are named identically (`App\Jobs\SendBroadcastBatchJob`, same constructor shape, deliberately mirroring hrm (3)'s Phase B job) and both physically share one `jobs` table (same DB). Giving both the same queue name (`broadcasts`) would have let either app's `queue:work` process dequeue and execute the OTHER app's job — since the class names match, PHP would silently run it with the wrong app's `BroadcastDeliveryService` (raw-insert vs. `Notification::send()`+FCM), no error, no warning. Fixed by giving `hrm-superadmin`'s job/batch a distinct queue name, `sa-broadcasts` — hrm (3)'s stays `broadcasts`. Verified separately: processing each app's queue with its own `--queue=` flag only ever touched that app's own test data, and the shared `jobs` table was empty of cross-app leftovers after each run.
- **Recipient-facing UI extension (not in the original phase spec, added to avoid a write-only audience mode)**: `superadmin_users`/`all_eligible` broadcasts targeting platform staff would otherwise have nowhere to be seen (the plan's UI section only specified a composer + history list for this app). Extended the pre-existing `super_admin_notifications` bell/list (`NotificationController`, `resources/views/layouts/app.blade.php`'s unread-count `@php` block, `resources/views/notifications/index.blade.php`) to also surface `broadcast_recipients` rows for `recipient_type=super_admin AND super_admin_id=auth()->id()` — a second section on the same notifications page, its own "Mark read" route (`notifications.broadcast-read`), merged into the same header bell unread count. **Deliberately not merged into `super_admin_notifications` itself** — that table stays reserved for automated system/ops alerts (see the module's original design note on why that mechanism isn't retired), this is a parallel display, not a dual-write.
- **Routes** (`hrm-superadmin/routes/web.php`, prefix `broadcast`): `index`/`show` open to any authenticated staff; `create`/`store`/`preview-count` gated `sa_role:superadmin,support`. No `cancel` route (nothing to cancel — sends are always immediate). **Route-ordering gotcha hit and fixed**: `/broadcast/{id}` must be registered AFTER the literal `/broadcast/create` etc., or a request to `/broadcast/create` would match `{id}='create'` first (Laravel matches in registration order) — caught before shipping, not left as a latent bug.
- **Sidebar**: "Broadcast Notifications" entry added right after "Feature Templates" in `resources/views/layouts/app.blade.php`, per the plan's own reasoning (both are "bulk action against a selected set of tenants" tools).
- **UI (updated 2026-09-25 — single-page + drawer, matching hrm (3)'s equivalent change)**: no more separate `/broadcast/create` page — that route/controller method/view are gone. `broadcast.index` (`hrm-superadmin/resources/views/broadcast/index.blade.php`) is the one page: `kpi5-card` stat cards (Total/Sent/Sending/Recipients Reached — this app has no centralized stylesheet, so this is a page-local copy of the exact `.kpi5-card` anatomy `dashboard.blade.php` already established, not a new pattern), a filter bar (status, audience type, from/to date, title search, all auto-submitting selects), the history table with a `Sr.No` column, and a "Send Broadcast" button opening `resources/views/broadcast/_send-drawer.blade.php` in a hand-rolled Bootstrap offcanvas (this app has no `<x-ui.drawer>` component — same offcanvas anatomy as the pre-existing `#templateDrawer`/`#applyDrawer` pair in `feature-templates/index.blade.php`, rendered inline here rather than fetch()-loaded since the form doesn't need lazy loading). Unlike hrm (3)'s version, the drawer's form is a **plain POST**, not AJAX — `store()` already redirected to the new broadcast's detail page on success and `back()->withErrors()->withInput()` on failure, so converting to a drawer needed no controller change; the only addition was auto-reopening the drawer via `@if($errors->any())` when validation fails, so a rejected submission doesn't leave the admin looking at a closed drawer with no visible reason why. - **Schema**: `broadcast_notifications` (the broadcast definition — title/body/action_url/action_label/`audience_type` enum/`audience_filters` JSON/channels JSON/priority/status/scheduled_at/sent_at/expires_at/snapshot counters) and `broadcast_recipients` (the per-recipient snapshot — `tenant_id` NOT NULL is the real security/scoping boundary, `UNIQUE(broadcast_id,user_id)` + `UNIQUE(broadcast_id,super_admin_id)` is the duplicate-prevention mechanism, `notification_id` links to the dual-written generic `notifications` row, `delivered_at`/`read_at`/`action_clicked_at` for read-tracking/stats). `broadcast_notifications` deliberately has **no** `tenant_id` column and its model does **not** use `TenantTrait` (a superadmin broadcast can span many tenants); `origin_tenant_id` is provenance-only ("which tenant's admin authored this"), never a scoping check — don't be tempted to scope this table by it.
- **Models**: `App\Models\Broadcast` (table `broadcast_notifications`, no `TenantTrait`), `App\Models\BroadcastRecipient` (no `TenantTrait` either — callers explicitly scope by `tenant_id`).
- **Audience resolver** (`App\Services\Broadcast\BroadcastAudienceResolver`): filters are `role[]`/`department_ids[]`/`designation_ids[]`/`branch_ids[]`/`user_ids[]`/`all:bool`. Semantics (product-confirmed, not guessable from code): AND across dimensions, OR within one dimension's multi-select, `user_ids[]` is **additive** (unioned on top of the filtered set, never intersected), `all=true` is mutually exclusive with every other filter. Tenant isolation is structural: `queryFor()` always starts from `App\Models\User::query()`, so `TenantTrait`'s global scope bounds every query to `app('current_tenant')->id` regardless of request payload — a forged cross-tenant `department_id`/`designation_id`/`branch_id` simply joins to zero rows (verified in a manual smoke test against real tenant data, not just by inspection). `department`/`designation` are matched via `UserJobDetail`'s columns of those exact names (not `department_id`/`designation_id`) — see Org Structure section above for why.
- **Composer orchestration** (`App\Services\Broadcast\BroadcastComposerService`): `validate()` (full, for `store()`) vs. `validateAudienceOnly()` (lighter, for the live recipient-count preview — doesn't require title/body, so adjusting audience filters before typing a title still shows a real count). `create()` runs audience-resolve + chunked (500/batch) `broadcast_recipients` snapshot insert **inside the same DB transaction** as the `broadcast_notifications` row (a crash mid-way must never leave an ambiguous "was 0 the real audience, or did it crash" state); delivery happens **after** commit since individual delivery failures are retryable and must never roll back an already-committed snapshot. `snapshotRecipients()` uses `BroadcastRecipient::upsert(..., ['broadcast_id','user_id'], ['updated_at'])` — retry-safe (a repeat call is a no-op on the unique constraint, not a duplicate-key error), verified by re-running it against a live broadcast and confirming the row count didn't change.
- **Delivery** (`App\Services\Broadcast\BroadcastDeliveryService`): dual-write — `broadcast_recipients` is this module's own source of truth for stats/read-tracking, and `Notification::send($usersChunk, new App\Notifications\BroadcastNotification($broadcast))` (the same batch primitive `ApprovalService::notifyLevel()` uses, try/catch, non-blocking) also fires per chunk so the send shows up for free in the existing mobile `notifications` table/API with **zero mobile-app changes** — `BroadcastNotification::toArray()` deliberately mirrors `AnnouncementNotification`'s exact `title`/`message`/`type` key shape since the mobile `NotificationController` reads those generically. Since `Notification::send()` doesn't return created ids, `notification_id` is backfilled by a small post-send lookup (`notifications` filtered by `type`+`notifiable_id`+`JSON_EXTRACT(data,'$.broadcast_id')`), not a mid-flight capture — verified working end-to-end in a manual smoke test.
- **Read-state sync, both directions closed (Phase B)**: the web notification center's "mark read" sets both `broadcast_recipients.read_at` and (if `notification_id` is set) calls `->markAsRead()` on the linked generic `notifications` row, in the same request. The reverse direction — mobile marks a notification read via the **unmodified** `Api\Notification\NotificationController` → propagate to `broadcast_recipients.read_at` — is `App\Observers\DatabaseNotificationObserver` (registered on `Illuminate\Notifications\DatabaseNotification` in `AppServiceProvider::boot()`), type-string-matched to `BroadcastNotification::class` only (cheap no-op for the other 24 Notification subclasses). Verified both directions manually.
- **Queue-based delivery (Phase B)**: `QUEUE_CONNECTION` switched from `sync` to `database` in **both** apps' `.env` (the `jobs`/`failed_jobs`/`job_batches` tables already existed, unused, in the shared DB — this was a config-only change). `BroadcastComposerService::create()` now calls `BroadcastDeliveryService::dispatchDelivery()` instead of delivering inline: it chunks undelivered `broadcast_recipients` ids (500/chunk) into `App\Jobs\SendBroadcastBatchJob` instances dispatched inside a `Bus::batch()` (queue `broadcasts`), whose `then()` callback flips the broadcast to `status=sent`/`sent_at`. `SendBroadcastBatchJob` mirrors `SendWebhookDelivery`'s bounded explicit-retry shape (`tries=1`, self-redispatch with a delay from a fixed `[1,5,15]`-minute schedule, **not** Laravel's default retry mechanism) — and, like `SendWebhookDelivery`, logs-and-returns-normally (does not rethrow) after exhausting retries, so one permanently-failed chunk doesn't mark the whole `Bus::batch` as failed; that chunk's rows just stay `delivered_at=null`, visible in the broadcast's own stats. `BroadcastDeliveryService::deliver()` (the old Phase A synchronous whole-broadcast path) is kept as a lower-level primitive, not currently called by the composer.
- **Scheduled + expiry commands (Phase B)**: `broadcast:send-scheduled` (`App\Console\Commands\SendScheduledBroadcasts`, scheduled `everyMinute()` — not the more common 5-minute cadence, since a 9:00am-scheduled broadcast should land at ~9:00-9:01) finds `Broadcast::dueToSend()` rows and **re-resolves the audience at fire time, not compose time** (a filter-based audience picks up new hires and drops anyone since deactivated automatically — `App\Models\User::where('status',1)` already excludes them, no special-casing needed) via `BroadcastComposerService::snapshotRecipients()`, then `dispatchDelivery()`. Since `app('current_tenant')` isn't bound outside an HTTP request, the command binds it itself per broadcast from `origin_tenant_id` before calling the resolver. `broadcast:expire` (`App\Console\Commands\ExpireBroadcasts`, scheduled `hourly()`) does two things in one pass, **stats-recompute before the status flip** (recomputing a broadcast's `delivered_count`/`read_count`/`action_click_count` from live `broadcast_recipients` rows only matches `status=sent` — running the flip first would leave a just-expired broadcast's final numbers stuck stale, since it'd already be `expired` by the time the recompute query ran): (1) refresh those snapshot counters for every `sent` broadcast, (2) flip `Broadcast::expirable()` (`sent` + `expires_at` past) to `status=expired`. Both commands verified end-to-end (dry-run + real run + queue processing) against live tenant data, then cleaned up.
- **RBAC**: new `broadcasts` module in `config/rbac.php` — `admin`/`hr` → `all`; `manager`/`employee` → `['view']` (can see broadcasts targeted to them; only admin/hr can compose/send). Route middleware: `feature:broadcast_notifications` on the whole `broadcast.*` group, `permission:broadcasts,{create,view,edit}` per action — same shape as `announcements`. New feature key `broadcast_notifications` (`default: true`, kept in sync in **both** `hrm (3)/config/features.php` and `hrm-superadmin/config/features.php` copies, matching the existing sync-by-hand convention).
- **Routes** (`routes/web.php`, prefix `broadcast`): composer `index`/`create`/`store`/`preview-count`/`show`/`cancel` (`App\Http\Controllers\Broadcast\BroadcastController`), recipient-facing `notifications/list`/`notifications/unread-count`/`notifications/{id}/read`/`notifications/mark-all-read` (`App\Http\Controllers\Broadcast\BroadcastNotificationCenterController`, open to every authenticated user regardless of the `broadcasts` permission — that gate is composer-only).
- **UI (updated 2026-09-25 — single-page + drawer)**: the composer is no longer a separate `/broadcast/create` page — that route/controller method/view are gone. `broadcast.index` (`resources/views/client/broadcast/index.blade.php`) is now the **one** page: KPI stat cards (Total/Sent/Scheduled/Recipients Reached, `kpi5-card`, reflecting all of the admin's broadcasts, not the current filter/page), a `.auto-submit` filter bar (status dropdown, from/to date, title search — same pattern as the Leave Balance report's filter bar), the history table with a `Sr.No` column, and a "Send Broadcast" button that opens `resources/views/client/broadcast/partials/send-drawer.blade.php` in a slide-over via the shared `<x-ui.drawer>` component (`data-bs-toggle="offcanvas" data-bs-target="#sendBroadcastDrawer"`, included through `@section('create-modal')` — same convention as the Biometric Terminals drawer). The drawer's own submit/preview-count JS lives in `index.blade.php`'s `@section('script-area')`, not the drawer partial (matching that same convention); on success it closes the drawer, toasts, and reloads the page rather than redirecting. Sidebar collapsed from a 2-item submenu to one link, "Broadcast" → `broadcast.index`, admin/hr only, `@feature('broadcast_notifications')` (Tier-1 "daily core" area, next to Announcement) — there's nothing left for a second sidebar entry to point at now that both actions live on one page. ## Summary: what's surprising / worth knowing before extending this app

1. Two approval mechanisms coexist per module (legacy direct single-approver code + the generic `ApprovalService` multi-level engine) — always check whether a tenant workflow is configured before assuming which path a request takes.
2. Several controllers carry explicit code-comment confessions of prior bugs that were fixed (Leave web-flow ignoring service result, Expense approval's dead-code ownership check, Loan deduction excluding lumpsum) — the comments are a good signal of where subtle logic previously broke and are worth reading in full before refactoring those areas.
3. Payroll has two calculation engines live in the codebase simultaneously (legacy flat + dynamic component-catalog "Phase 2" engine) — the dynamic engine **is** live for any tenant with `tenants.payroll_dynamic_ui_enabled = 1` (its docblock used to claim otherwise; corrected 2026-09-16). Always check that flag before assuming which engine produced a given payslip — see [`docs/payroll-dynamic-engine-migration.md`](payroll-dynamic-engine-migration.md).
4. No dedicated Onboarding controller/module exists despite it appearing in earlier project notes — don't assume `onboarding_tasks`-style functionality is live without checking `docs/database.md` and re-grepping the codebase.
5. Status vocabularies are **not** consistent across modules: Leave uses lower-case `pending/approved/cancelled`; Requests (WFH/Travel) uses upper-case `PENDING/APPROVED/REJECTED/CANCELLED`; Loan/Expense have their own sets. Never assume one module's status strings apply to another.
