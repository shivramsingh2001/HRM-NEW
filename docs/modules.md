# Modules Reference

Functional/business-logic reference for the Laravel HRMS app at `D:\HRMNEW\hrm (3)`. Route line numbers refer to `routes/web.php` (admin panel, Blade) and `routes/api.php` / `routes/api_v1.php` (mobile/external API) as they stood 2026-09-16. Business rules below were read directly from controller/service code — not inferred — but controllers are large (several exceed 1,000 lines) so treat each module section as "verified highlights," not an exhaustive line-by-line spec. Re-grep the cited file before relying on an exact rule for anything payroll- or money-related.

## Cross-cutting concerns (apply across most modules below)

**Multi-tenancy**: every table has `tenant_id`; a `tenant` middleware group wraps all of `web.php`/`api.php`. See `docs/architecture.md` for the resolution mechanism.

**Two permission layers, both in active use, not a clean migration**:
- Coarse: `role:admin`, `role:hr`, `role:manager`, `role:employee` (or comma lists like `role:admin,hr`) — `app/Http/Middleware/RoleMiddleware.php`.
- Fine-grained: `permission:{module},{action}` — `app/Http/Middleware/EnsurePermission.php` → `App\Services\RbacService::can()`. `admin` role always bypasses. Used alongside `role:` in the same route file (e.g. leave, expenses, overtime, meetings, payroll, task approval). Controllers additionally call a `scopeCoversOwner($authUser, $module, $action, $ownerUserId)` helper (seen in `LeaveController`, `ExpenseController`) to check whether the acting manager's scope actually covers the specific employee being approved — this replaced an earlier bug where any manager could approve any employee's request.
- `feature:{key}` — `app/Http/Middleware/EnsureFeatureEnabled.php` → `App\Services\FeatureService::enabledForCurrentTenant()`. Gates whole modules by subscription plan (currently applied to `payroll` and `recruitment` route groups). No tenant context = allow.

**Generic multi-level Approval Workflow Engine** (`App\Services\Approvals\ApprovalService`, Tier 2/T2-A): a tenant can configure a named workflow (`approval_workflows` + `approval_workflow_steps`, managed at Settings → Approvals, `app/Http/Controllers/Settings/ApprovalWorkflowController.php`) for a request type. `ApprovalService::decide($type, $subject, $actor, $action, $remarks)` is called from the *old* single-approver controller code; it returns `null` if no workflow is configured for the tenant (falls through to legacy direct-approve code unchanged), or drives the subject through the configured levels (role / user / reporting_head / department_head approvers, quorum `all` or first-wins, per-level SLA with `auto_approve` / `escalate` / `notify` breach action via a scheduled `tick()`). Registered handlers (`request_type => handler class`) in `ApprovalService::HANDLERS`:
  - `regularization` → `RegularizationApprovalHandler`
  - `overtime` → `OvertimeApprovalHandler`
  - `leave` → `LeaveApprovalHandler`
  - `payroll_revision` → `PayrollRevisionApprovalHandler`
  - `payroll_bonus` → `PayrollBonusApprovalHandler`
  - `payroll_run` → `PayrollRunApprovalHandler`
  Approval delegation (`approval_delegations`, date-scoped) is honored in `currentApprovers()`. Also supports delegate-aware notifications via `App\Notifications\CustomNotification`.

**Notifications**: most write-actions fire an in-app `Notification` (Laravel notifications table) plus FCM push (`App\Services\FirebaseService`) via per-module `*NotificationService` classes (`LeaveNotificationService`, `ExpenseNotificationService`, `OvertimeNotificationService`, `AttendanceNotificationService`, `AttendanceRegularizationNotificationService`, `TaskNotificationService`, `RequestNotificationService`, `MeetingNotificationService`, `AnnouncementNotificationService`, `ExpensePaymentNotificationService`). These are consistently wrapped in `try/catch` so a notification failure never blocks the underlying transaction.

- Export: `export/excel`, `export/pdf` (employee list).

## Org Structure: Branches, Departments, Designations, Employment Types

- **Attendance Location vs. Branch (2026-09-20 split)**: what used to be a single `branches`/`Branch` concept has been split into two genuinely separate modules, since it always conflated "where can this employee check in from" with "which organizational branch does this employee belong to":
  - `App\Http\Controllers\AttendanceLocation\AttendanceLocationController` (`App\Models\AttendanceLocation`, table `attendance_locations`, routes `attendance-location.*`) — purely the attendance-geofencing entity (name + lat/long + `radius` + `geofence_enabled`). Read by `Api\Attendance\AttendanceController`'s clock-in/out geofence check via `user_job_details.office_branch` (unchanged column name; `0` = "any active, geofence-enabled location"). UI at `client/attendance-location/attendance-location.blade.php` — the all-blue card grid + Leaflet map picker (kept from the original page) + a real delete-confirmation modal (the old page's delete button was dead — JS referenced a modal that didn't exist anywhere in the file).
  - `App\Http\Controllers\Branch\BranchController` (`App\Models\CompanyBranch`, table `company_branches`, routes `branch.*`) — the actual organizational Branch: name/address/contact/`branch_head` (FK → users), **no** lat/long/radius/geofence fields at all. Optional — `user_job_details.branch_id` (nullable, new) is only populated by companies with multiple physical branches; a single-location company never touches it. `detail()` shows a read-only profile + "Branch Members" table (mirrors Department's members table) with an **Assign Employees** bulk action (`assignEmployees()`, `assign_type` of user/department/all, adapted from `ShiftController::getUserIdsForAssignment()`) that writes `branch_id` for many employees at once. Gated `role:admin,hr` for mutations, `permission:branches,view` (company-wide, all roles) for reads — the first of the org-structure modules to get real RBAC registration (`config/rbac.php`'s `branches` module); Department/Designation still rely on Blade-level role checks only, unchanged.
  - `ApprovalWorkflow::matchesUser()`'s `applies_to` scoping (`app/Models/ApprovalWorkflow.php`) was split the same way: the pre-existing `branches` key (which actually checked `office_branch`) is now `attendance_locations`; a new `branches` key checks the new organizational `branch_id`. No live data existed for either key at the time of the split (verified before renaming), so no data migration was needed.
  - Both `AttendanceReportController`'s branch-wise attendance report (`DB::table('branches')` → `attendance_locations`) and its two views were updated to match; labels relabeled "Attendance Location Wise" for clarity. A near-identical, unrouted dead-code duplicate of that report (plus an unused `updateEmployeeBranch()`) still sits in `TeamController.php:1810-2510` — left untouched, pre-existing and out of scope.
- `App\Http\Controllers\Department\DepartmentController`, `App\Http\Controllers\Designation\DesignationController` — simple CRUD, index/create/update/detail pattern, no delete route exposed for either. Both list pages (`client/department/department.blade.php`, `client/designation/designation.blade.php`) use the same all-blue card theme from `client/announcement/all.blade.php` (view + edit icons on each card, edit opens a shared modal populated via JS `data-*` attributes); their detail pages (`department-detail.blade.php`/`designation-detail.blade.php`) are read-only — editing was moved off of them onto the list-page card. **Note**: view/edit icon visibility differs pre-existingly between the two modules — Department gates both view and edit to `admin`/`hr`; Designation gates view to `admin`/`hr` but edit to `admin`/`manager` (carried over unchanged from the original detail-page edit button's guard) — not unified during this pass since it wasn't asked for.
- Employment types: model `EmployementType` exists (note the typo is baked into the class/table name); no dedicated controller found in `routes/web.php` — likely managed as a lookup elsewhere (check Settings or seeders if this needs UI).
- Roles/permissions: `roles`, `role_permissions` tables (per `docs/database.md`); runtime checks go through `RbacService`, not a dedicated CRUD controller found in this pass.

## Attendance

- Web: `App\Http\Controllers\Attendance\AttendanceContoller` (sic — typo preserved from codebase) — calendar view, sessions.
- Mobile: `App\Http\Controllers\Api\Attendance\AttendanceController` (huge, ~1600+ lines) — `clockIn`, `clockOut`, `history`, `trackLocation`/`trackBatch` (GPS breadcrumbs, throttled `location-ingest`), `today`, `todayLocations`, `regularizationStore` + regularization view/approval endpoints.
- **Clock-in rules** (`AttendanceController::clockIn`, `app/Http/Controllers/Api/Attendance/AttendanceController.php`): requires `lat`, `long`, `address` (min 5 chars); resolves the user's shift for the day; **night-shift date rollback** (now `AttendanceCalculator::resolveAttendanceDate()`, lifted out of this controller so every punch source agrees) — if the shift end time is before its start time (or ends ≤04:00 and starts ≥20:00) and the clock-in happens between 00:00–05:59 before the shift's start hour, the attendance row is dated to the *previous* calendar day; checks for an approved WFH/Travel `Request` covering the date. Geofence/branch resolution is unchanged. The actual write (and the open/closed-session check) is delegated to `AttendancePunchService::capture()` — see "Attendance — multiple punches per day" below. Failed attempts are logged via `createFailureLog()`.
- **Attendance — multiple punches per day (added 2026-09-23)**: `tenants.allow_multiple_punches` (default `false`, toggled on the Attendance Policy settings page alongside `late_halfday_enabled`) controls whether an employee can clock in again after clocking out. `attendances` is no longer written directly by any punch source — it is a **materialized rollup** of the new `attendance_punches` table (one row per raw Clock In/Out event, from mobile GPS, web, manual/admin, biometric, or a future kiosk source), computed the same way for both flag values so there is one derivation path, not two parallel worlds:
  - `App\Services\Attendance\AttendancePunchService::capture(PunchInput $input)` is the single funnel every source calls. Enforces: an `in` while a session is already open is always rejected (both flag values); when `allow_multiple_punches=0`, an `in` is *also* rejected once any session has already completed that day (byte-identical to the pre-2026-09-23 "one clock-in/out pair per day" behaviour); an `out` with no open session is rejected. Also handles period-lock checks, a debounce window (`config('biometric.dedupe_window_seconds')`, shared with the biometric pipeline), and `client_ref`-based idempotency for mobile offline-sync retries. The "is there an open session" lookup is bounded to a few days either side of the incoming punch's own timestamp (not the server's wall clock) so a punch from an unrelated period can never be mistaken for a currently-open session.
  - `App\Services\Attendance\PunchSessionCalculator` is the pure (no-DB) pairing/aggregation algorithm: sorts a day's punches by `punched_at` (so out-of-order/delayed-sync arrivals self-correct), pairs `in`→`out` into sessions, sums worked seconds across sessions, and derives `clock_in` (first session's in), `clock_out` (**null while any session is open, even if an earlier session already closed today** — this preserves `clock_out IS NULL` as "still clocked in" everywhere that invariant is relied on), `late_minutes` (from the first in), and `early_departure_minutes`/`overtime_minutes`/`attendance_status` (from the last out, once the day is closed). An `out` with no preceding `in` (biometric replay/clock skew) is excluded from the math and flagged via `attendances.metadata.needs_review`, never silently dropped.
  - `App\Services\Attendance\AttendanceRollupService::recompute()` is the bridge back to the existing world: it calls the calculator above, then writes the result through the **unmodified** `AttendanceEntryService::record()` funnel — so period-lock enforcement, the `attendance_logs` audit trail, `LatePolicyService`/`AttendanceSummaryService` recompute, and `AttendanceDomainEvent` emission all keep working exactly as they do for every other write path.
  - The mobile `clockIn()`/`clockOut()` controller methods keep all of their existing geofence/WFH/night-shift-rollback logic verbatim; only the final "write the row" step was swapped for a call into `AttendancePunchService::capture()` — this also closes a pre-existing gap where the mobile path bypassed period-lock checks and never emitted `AttendanceDomainEvent`. `BiometricAttendanceService::apply()` (see Biometric section below) branches on the tenant flag: `=0` tenants keep their original single-pair-fold behaviour completely unchanged; `=1` tenants route through the same `AttendancePunchService` funnel so a 3rd+ punch opens a new session instead of being discarded.
  - New read-only mobile endpoints, additive: `GET /api/user/attendance/punches?date=` (raw punches + paired sessions for one day) and `GET /api/user/attendance/current-session` (cheap open/closed status for the clock-in/out button state).
  - Historical `attendances` rows were backfilled into `attendance_punches` on migration (`source='backfill'`, one synthetic `in`/`out` pair per existing `clock_in`/`clock_out`); `attendances.session_count` is `1` for every pre-2026-09-23 row and every `allow_multiple_punches=0` day going forward.
  - Reports/analytics/payroll/the AI export API/the B2B `AttendanceV1Controller` were **not changed** — they all read `attendances`/`attendance_summaries`, whose values are unaffected for `allow_multiple_punches=0` tenants by construction (same funnel, same numbers).
- **Late/half-day policy** (`App\Services\Attendance\LatePolicyService::recalculateMonth`) — Feature B, the *sole writer* of `attendances.effective_status`/`day_fraction`/`policy_note`, deterministic/idempotent, re-runnable any time:
  - Manual rows (`attendance_type = manual` or has `marked_by`) are authoritative and never reclassified from worked hours.
  - `on_leave`/`absent`/`holiday`/`weekoff` → 0.0 day fraction; `half_day`/`first_half_leave`/`second_half_leave` → 0.5.
  - Otherwise worked seconds are computed (`AttendanceCalculator::workedSeconds`, capped at 24h) and classified by `AttendancePolicySnapshot::classify()` against the tenant's policy in force **on the 1st of that month** (a later policy change never retroactively re-grades a closed month).
  - Each `late` day increments a per-user monthly late counter; once the count exceeds the tenant's `monthlyLateAllowance` (Settings → Attendance Policy, `role:admin,hr` only, `routes/web.php:532`), the day is downgraded to `half_day` (0.5 fraction) instead of `present` — only if `lateHalfdayEnabled` is on. A day that was regularized is never counted as late and never downgraded.
- Attendance analytics/anomaly review: `App\Http\Controllers\Analytics\AttendanceAnalyticsController`, gated `role:admin,hr,manager`, backed by `App\Services\Analytics\AttendanceAnalyticsService` / `AnomalyScanner`.
- Team-level manual marking + attendance log/summary: `App\Http\Controllers\Team\TeamController` (`routes/web.php:280-297`) — `mark-attendance` restricted to `role:admin,hr,manager`; `attendance-log` gated `permission:team,view`.
  - `team.index` (`/team/members`, `TeamController::team()`) list adds a debounced name/employee-id/email search box and a Branch filter/column (`user_job_details.branch_id` → `company_branches.name`, via the existing `UserJobDetail::branch()` relation), alongside the pre-existing date/status filters. Its Mark Attendance modal uses the shared `.compact-modal`/`.compact-modal-plain` chrome (`btn-modal-cancel`/`btn-primary` buttons) instead of page-local `.btn-primary-custom` classes.
  - `team.member-detail` (`/team/member-detail/{id}`, `TeamController::viewUserProfile()`) shows a "Team" tab when the viewed employee's `role` is `manager`, listing that manager's direct reports (`getTeamMembers($authUser, $today, $managerId)` — the same private helper as `team.index`, given an explicit manager id instead of the RBAC-scoped auth user) with today's attendance status/punch times; each row links back into `team.member-detail` for that employee. The attendance calendar's month navigation is native FullCalendar prev/next (no separate Apply/Reset filter form).
- Reports: `App\Http\Controllers\Report\AttendanceReportController` — day/hourly/overall/employee-wise/branch-wise/monthly-summary variants, each with an `export` counterpart, all under `role:admin,hr,manager`.

## Overtime

- Web: `App\Http\Controllers\Attendance\OvertimeController` (self-service `overtime.*` routes) + `App\Http\Controllers\Attendance\OvertimeSettingController` (tenant policy, `permission:overtime,manage`).
- Mobile: `App\Http\Controllers\Api\Attendance\OvertimeController`.
- **Business rule** (`OvertimeController::store`, `app/Http/Controllers/Attendance/OvertimeController.php:100`): one request per user per date (duplicate blocked); `overtime_hours` must be 0.5–24 and ≤ tenant's `max_hours_per_day` (from `overtime_settings`, tenant-specific row or a global fallback row with `tenant_id = null`); **auto-approval**: if the tenant's policy has `require_approval = false`, or `overtime_hours <= auto_approve_limit`, the request is created with `status = approved` immediately (no approver step) — otherwise `status = pending`.
- Approve/reject gated `permission:overtime,approve`; view-all/show gated `permission:overtime,view`. Also routed through `ApprovalService` (`OvertimeApprovalHandler`) if a tenant workflow exists.
- `App\Services\Attendance\OvertimeApprovalService::bulkApprove(User $actor, int $tenantId, array $requestIds)` — single source of truth for "bulk-approve these pending requests as this actor": `RbacService::can(...,'overtime','approve')` gate, `scopeFor()` restricts to reportees when scope is `team`, direct status flip (bypasses `ApprovalService`'s multi-level workflow by design — matches this method's own precedent). Used by `OvertimeController::bulkApprove()` (currently **unrouted** — no `web.php`/`api.php` route wires it up, pre-existing dead code, not fixed as part of extracting this service) and by `MonthlyPayrollController::update()`'s "include non-approved overtime" flow below.

## Shift Management

- **Company-wide vs. employee-wise mode**: `tenants.custom_shifts_enabled` (toggle at `Settings\ShiftSettingsController`, `shift-settings.*`, `role:admin,hr`, **not** gated by the `shifts.custom` middleware below so the toggle screen is always reachable). OFF = the whole company runs on one fixed shift (`tenants.default_shift_id` + `default_weekoff_days`, applied company-wide by `regenerateWeeklyOffs()`); every other `shift.*` route is unreachable while OFF. ON = per-employee assignment via `shift_assignments`/`user_shifts` below. `App\Services\Attendance\TenantShiftResolver::forUserDate($userId,$tenantId,$date)` is the single resolver for "what shift applies to this user on this date" — OFF path unconditionally returns the tenant default (status not checked, so an admin can still edit a disabled default); ON path is an exact-date lookup on `user_shifts` (`Shift.status=1` required, else `null`). **This resolver's code has not changed** since the Permanent/Flexible feature below shipped — see the write-time note.
- Definitions CRUD: `App\Http\Controllers\Shift\ShiftController` (`index/store/update/change-status/destroy`, `shift.*` routes, `role:admin,hr`) manages `shifts` rows (name/times/grace/break/color; `total_hours` computed server-side via `computeTotalHours()`, handles midnight-crossing when `end_time <= start_time`).
- Roster/assign UI: `shift.roster` (`role:admin,hr,manager`, manager sees only their reportees) — two tabs: **Roster** (day/week/month grid) and **Existing Assignments** (admin/hr, filterable list + bulk edit/delete/export, `getUserShiftsData`). "Assign Shift" is a modal on this page (`POST shift.assign`), not a standalone page.
- **Permanent vs. Flexible assignment types (added 2026-09-18)** — see [[hrm-shift-management-overhaul-plan]] memory for the full design rationale:
  - **`shift_assignments`** table (no migration-less legacy table like `shifts`/`user_shifts` — this one has a real migration) is the append-only source of truth: `type` enum(`permanent`/`flexible`), `start_date`/`end_date` (`end_date` null = open-ended, only legal for `permanent`), `status` enum(`active`/`superseded`/`ended`/`cancelled`), `superseded_by_id` self-referencing chain (no FK, matching the legacy no-FK pattern on `shifts`/`user_shifts`). Never hard-deleted.
  - **`user_shifts` is unchanged in shape** and is now a **generated per-day cache** materialized from `shift_assignments` by `App\Services\Shift\ShiftMaterializer` — every pre-existing direct reader of `user_shifts` (mobile/AI shift-plan endpoints, `CheckMissedCheckIns`, the 3x-duplicated `getUserShiftForDate()`, `TenantShiftResolver` itself) keeps working unmodified. A new nullable `user_shifts.shift_assignment_id` column points back at the source row (null for pre-2026-09-18 rows or a raw single-day `updateUserShift` edit).
  - **Priority rule**: Flexible always wins over Permanent for the dates it covers (the override case — a Flexible assignment is explicitly allowed to be created inside an active Permanent's range); when a Flexible range ends, the user automatically reverts to whichever Permanent is active, with zero manual step. This is enforced **at materialization write time**, not by adding branching logic to `TenantShiftResolver` — `ShiftMaterializer::materializeFlexible()` always overwrites a `user_shifts` row that a Permanent assignment produced, and only respects `override_existing` when the existing row came from *another* Flexible assignment.
  - **Permanent assignments are open-ended and self-maintaining**: `ShiftMaterializer::materializePermanentHorizon()` caches a rolling **120-day horizon** (`ShiftMaterializer::PERMANENT_HORIZON_DAYS`) from an open-ended assignment; the scheduled command `shift:roll-permanent-horizon` (daily, `routes/console.php`) tops every active Permanent assignment's cache back up to `today+120` — this is what removes the need to ever manually re-assign a standing shift (the original pain point this feature solved; the old `assignShift` flow required re-running the same range every ~90 days).
  - **Auto-supersede**: assigning a new Permanent shift to a user who already has one active automatically closes the old one (`end_date = new.start_date - 1`, `status='superseded'`, chained via `superseded_by_id`) — no separate "end it first" step. Explicitly ending one (no replacement) is the "End Permanent Shift" action → `ShiftAssignmentService::endPermanent()`.

## Asset Management (2026-09-22)

Full asset lifecycle module — categories/types, registration with a system-generated Asset ID, purchase/warranty/vendor/branch detail (all nullable except the core identity/status fields), employee assignment with **blocking acceptance**, return, transfer, repair, damage/loss, retirement, and disposal. New tables: see `docs/database.md`'s "Assets" section.

- **State machine, not `ApprovalService`**: transfer/disposal are direct actions gated by RBAC permission (not a second approver) — deliberately not built on the generic multi-level `ApprovalService` (§ "Approvals" below), which is purpose-built for hierarchical manager-approval chains, not a multi-branch custody state machine. `app/Services/Asset/AssetLifecycleService.php` is the single choke point for every transition (`register`/`assign`/`accept`/`returnAsset`/`transfer`/`sendForRepair`/`completeRepair`/`reportDamageOrLost`/`resolveDamageReport`/`retire`/`dispose`); each method validates the legal transition from the asset's current status, writes one `asset_histories` row, calls `AuditLogger::record('tenant_user', ...)`, and fires `AssetNotificationService` — the same "domain history + audit log + notification" triple-write pattern the Requests module uses.
- **Acceptance is blocking**: `assign()`/`transfer()` put the asset into `pending_acceptance` and leave `assets.current_assignee_id` null; only `accept()` (by the assignee, or an admin/HR "force accept", logged as `ACCEPTANCE_FORCED`) moves it to `assigned` and sets `current_assignee_id`. A transfer re-enters `pending_acceptance` for the new holder — it does not skip the acceptance gate.
- **Repair doesn't end an assignment**: sending an assigned asset for repair flips `assets.status` to `in_repair` (remembering the prior status in `pre_repair_status`) without touching the active `asset_assignments` row — the same employee gets the same asset back on completion.
- Controllers, `app/Http/Controllers/Asset/`: `AssetController` (register/list/detail/edit/delete, bulk status/category/branch update, CSV export, employee self-service `myAssets`/`myAssetShow`), `AssetLifecycleController` (one thin action per transition — mirrors `TeamController::markAttendance()`'s wrapper shape), `AssetCategoryController`/`AssetTypeController`/`VendorController` (small reference-data CRUD, mirror `BranchController`), `AssetAttachmentController` (mirrors `ProjectController::storeAttachment()`'s `public_path('uploads/assets/...')` + UUID-filename convention exactly, no `Storage::disk()`).
- **Ownership bypass for accept/return**: an employee may always accept/return an asset currently assigned to them (`AssetAssignment.user_id === auth()->id()`), independent of the coarse `assets` RBAC grant — same "everyone can act on their own record" pattern as Loans/Requests. Routes: `routes/web.php` `assets.*`/`asset-categories.*`/`asset-types.*`/`asset-vendors.*`/`my-assets.*`, each gated `permission:assets,{view|create|edit|delete|manage}`.

## Requests (WFH / Travel)

- `App\Http\Controllers\Attendance\RequestController` (web) — self-service `index`/`store`/`update`/`destroy` (soft-cancel, see below), attachment delete/download, stats, export; manager surface at `manager/requests*` (`managerIndex`/`managerShow`/`approve`/`reject`/`bulkApprove`/`managerExport`/`managerStats`). `App\Http\Controllers\Api\Attendance\RequestController` (mobile, `Api\Attendance` namespace despite having nothing to do with clock-in/out) mirrors the same capability set: `type`/`store`/`view`/`view_all`/`updateStatus`/`show`/`update`/`cancel`.
- **RBAC is now consistently enforced on both surfaces** (2026-09-17 pass) via `config('rbac.php')`'s `requests` module matrix (`admin`/`hr` → `all`, `manager` → `['view' => 'team', 'approve' => 'team']`, `employee` → `['view' => 'own']`) and the shared `AuthorizesByScope` trait (`applyScope()` for list queries, `scopeCoversOwner()` for single-record checks) — previously the web controller used ad hoc `$user->role == 'admin'` checks that silently ignored any custom role's `requests` grant, while the mobile controller already did this correctly; both now match. The manager-facing routes (`manager.requests`/`.show`/approve/reject/bulk-approve/export/stats on web, `manager/request/view`/`update-status` on mobile) also carry `permission:requests,view`/`permission:requests,approve` middleware as defense-in-depth; self-service create/update/cancel routes stay unmiddlewared (ownership-checked in-controller), matching the Leave/Attendance-Regularization convention.
- **Cancel is a soft status change, not a delete** (`destroy()` on web / `cancel()` on mobile): sets `status = CANCELLED` (preserving the row, its `request_attachments`, and a `request_histories` `CANCELLED` entry) rather than hard-deleting. Per `Request::canBeCancelled()`, both `PENDING` and `APPROVED` requests can be cancelled — cancelling an already-approved request notifies the reporting head/HR/admin via `RequestNotificationService::notifyRequestCancelled()`.
- **Overlap rule** (`Request::scopeOverlapping()` on the model, shared by web `store()`/`update()` and mobile `store()`/`update()`): a new/edited request is rejected if the user already has a `PENDING` or `APPROVED` request whose date range overlaps (start/end/containment all checked) the new one — extracted to one model scope so the rule can't drift between web and mobile.
- Attachments are uploaded to and served from `public/uploads/requests/attachments` (plural, one consistent convention on both surfaces and both store/update — previously 3 different, mutually inconsistent directory names were used across web `store()`/`update()` and mobile `store()`, causing 404s on any attachment link). `requests.download-attachment` (web) forces a real download via `response()->download()` rather than relying on the raw public URL.
- Every state-changing action (create/update/cancel/approve/reject) now also calls the shared `AuditLogger::record()` (actor_type `'tenant_user'`, action strings `requests.created`/`.updated`/`.cancelled`/`.approved`/`.rejected`) in addition to the module's own `request_histories` trail — previously this module had no `AuditLogger` coverage at all.
- Notifications (`RequestNotificationService`): `notifyRequestSubmitted`/`notifyRequestApproved`/`notifyRequestRejected`/`notifyRequestCancelled`, all dual-channel (FCM + DB `notifications`). Now wired into every relevant action on both web and mobile — previously mobile never called this service at all, web's `reject()` had a dead `// TODO`, and `bulkApprove()` sent nothing.
- Status vocabulary is upper-case here: `PENDING`, `APPROVED`, `REJECTED`, `CANCELLED` (distinct from Leave's lower-case `pending`/`approved`/`cancelled` — don't assume the two modules share a status enum).
- `request_types` table defines the type catalog (WFH/Travel per `docs/database.md`); `RequestType` model.
- `daily_reports`/`DailyReport` (WFH daily work-log table) has no controller or route anywhere referencing it — intentionally left dormant/unimplemented, not a bug.
- Not integrated with the generic `ApprovalService` multi-level workflow engine (no `requests` handler registered) — this module remains single-approver only; a future enhancement, not planned here.

## Summary: what's surprising / worth knowing before extending this app

1. Two approval mechanisms coexist per module (legacy direct single-approver code + the generic `ApprovalService` multi-level engine) — always check whether a tenant workflow is configured before assuming which path a request takes.
2. Several controllers carry explicit code-comment confessions of prior bugs that were fixed (Leave web-flow ignoring service result, Expense approval's dead-code ownership check, Loan deduction excluding lumpsum) — the comments are a good signal of where subtle logic previously broke and are worth reading in full before refactoring those areas.
3. Payroll has two calculation engines live in the codebase simultaneously (legacy flat + dynamic component-catalog "Phase 2" engine) — the dynamic engine **is** live for any tenant with `tenants.payroll_dynamic_ui_enabled = 1` (its docblock used to claim otherwise; corrected 2026-09-16). Always check that flag before assuming which engine produced a given payslip — see [`docs/payroll-dynamic-engine-migration.md`](payroll-dynamic-engine-migration.md).
4. No dedicated Onboarding controller/module exists despite it appearing in earlier project notes — don't assume `onboarding_tasks`-style functionality is live without checking `docs/database.md` and re-grepping the codebase.
5. Status vocabularies are **not** consistent across modules: Leave uses lower-case `pending/approved/cancelled`; Requests (WFH/Travel) uses upper-case `PENDING/APPROVED/REJECTED/CANCELLED`; Loan/Expense have their own sets. Never assume one module's status strings apply to another.
