# CLAUDE.md — HRM Project Instructions

This is a Laravel 11 (PHP 8.2) multi-tenant HRMS: a Blade-based web admin panel plus a JSON API
that serves a Flutter mobile app and third-party integrations. Single database, `tenant_id`
scoping on almost every table.

## Read the docs before starting any task

Full documentation lives in `docs/`. **Read the relevant file(s) before writing code** — they
were generated by directly inspecting this codebase (real file paths, class/method names, route
examples, live DB schema) specifically to avoid re-discovering the project from scratch every
session.

| File | Read this when you need to... |
|---|---|
| [`docs/architecture.md`](docs/architecture.md) | Understand folder structure, controller/service/repository patterns, middleware, routing, auth (JWT — not Sanctum), multi-tenancy internals, or general coding conventions. Read first for any backend task. |
| [`docs/modules.md`](docs/modules.md) | Work on a specific feature/module (attendance, leave, payroll, expense, loan, recruitment, performance, etc.) — controllers, routes, permissions, real business rules, and the generic `ApprovalService` workflow engine. Read the relevant module section before touching that feature. |
| [`docs/ui-guidelines.md`](docs/ui-guidelines.md) | Touch any Blade view — CSS stack (Bootstrap 5 + commercial theme, **not** the Tailwind/Vite scaffold, which is unused), design tokens, the `<x-ui.*>` component library, tables/modals/forms/badges/icons conventions. |
| [`docs/database.md`](docs/database.md) | Write queries, add columns/tables, or reason about relationships — full live schema (148 tables) grouped by domain, enum values, indexes, which tables have real FK constraints vs. app-only relationships. |
| [`docs/payroll-dynamic-engine-migration.md`](docs/payroll-dynamic-engine-migration.md) | Touch anything related to moving a tenant from the legacy flat payroll engine to the dynamic component-catalog engine, or `tenants.payroll_dynamic_ui_enabled` — what already exists (`payroll:backfill-component-catalog`, `payroll:resync-drifted-structures`, `payroll:engine-diff`, `payroll:cutover-tenant`), what changes on cutover, and the production rollout checklist. |

## Working rules

1. **Reuse before you build.** Check `docs/modules.md` for existing controllers/services and
   `docs/ui-guidelines.md` for existing Blade components (`resources/views/components/ui/*`)
   before writing new ones. This codebase has a lot of near-duplicate logic already — don't add
   another variant if one exists.
2. **Match existing patterns, not idealized ones.** The docs describe what the code *actually*
   does (e.g. fat controllers, minimal repository usage, two coexisting API/payroll "eras").
   Follow the prevailing pattern in the module/area you're editing rather than introducing a new
   architecture unprompted.
3. **Don't re-derive what's already documented, and don't re-analyze the whole project per task.**
   Don't re-run full-codebase greps, re-dump the whole DB schema, or re-read every controller in a
   module if `docs/` already answers the question. Use `git status` / `git diff` to see exactly
   what changed recently instead of re-scanning the tree — that's the fast, cheap way to catch up,
   not a fresh full-project analysis. Do spot-check the specific files/queries you're about to
   modify — the docs are a map, not a substitute for reading the code you're changing.
4. **Two API eras coexist** (`routes/api.php` legacy mobile API vs `routes/api_v1.php` Tier 2
   public API with `ApiClient` auth). Don't mix their conventions — see `docs/architecture.md` §
   "API response conventions".
5. **Keep `docs/*.md` synchronized with the code, every time, not just for "major" changes.**
   Whenever a change touches any of the following, update the matching doc file in the *same*
   change (not as a follow-up):
   - Controllers, routes, or middleware → `docs/architecture.md` and/or `docs/modules.md`
   - Database structure (tables, columns, indexes, relationships) → `docs/database.md`
   - Blade components, layout, or other UI patterns → `docs/ui-guidelines.md`
   - Business rules, approval flows, or module workflows → `docs/modules.md`
   A change that's purely internal (e.g. a bug fix with no behavior/shape change visible to the
   doc's audience) doesn't need a doc edit — but if in doubt, update it; stale docs are worse than
   a redundant one-line edit.
6. **Use git to verify docs and code actually agree.** Before starting work in an area, and again
   before calling a task done, use `git status`/`git diff`/`git log` on the files you touched to
   confirm the change is fully reflected in the relevant `docs/*.md` (and vice versa — that nothing
   in the diff contradicts what the docs claim). This is the review mechanism; don't rely on memory
   of what you intended to update.
7. **Never modify application behavior just to make documentation easier.** These docs describe
   the app as it is; keep it that way unless the user asks for a code change.

## Known project quirks (see docs for detail)

- Auth is JWT (`php-open-source-saver/jwt-auth`) for the API guard, session-based for the web
  panel. No Sanctum in this codebase despite older references to it.
- DB schema is **not** fully captured by `database/migrations/` for the oldest/legacy tables —
  `docs/database.md` documents the live schema pulled directly from MySQL (regeneration command
  included at the bottom of that file).
- Payroll has two calculation engines coexisting: legacy flat (still the default; `permission:payroll,*`
  guards every route as of the Phase 1 audit-fix pass) and a dynamic component-catalog engine that
  **is live** for any tenant with `tenants.payroll_dynamic_ui_enabled = 1` (not "not yet wired" —
  that was a stale docblock claim, corrected 2026-09-16). See
  [`docs/payroll-dynamic-engine-migration.md`](docs/payroll-dynamic-engine-migration.md) before
  touching cutover/migration logic.
- RBAC: `permission:{module},{action}` middleware + `RbacService` is the actually-enforced system
  on payroll routes (wired in as of the Phase 1 audit-fix pass, 2026-09-16) — the plain `role:`
  string-column check still exists elsewhere in the app and is being phased out module by module;
  don't assume `role:` is authoritative for a module without checking its routes first.
- Frontend: Bootstrap 5 + a purchased admin theme is what's live. Tailwind/Vite config in the repo
  is unused Breeze scaffolding — don't build new UI against it.
